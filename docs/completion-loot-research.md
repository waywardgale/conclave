# Completion loot and offline recipients

Research date: 2026-09-26. Target: Minecraft Java 26.2. These are native source facts and labeled integration inferences, not accepted Conclave policy or an implemented reward adapter.

## Evidence

Inspected Mojang's cached official client artifact with `javap`, including private method bytecode and lambda bootstrap references. The artifact contains the named common and server classes used below. Its SHA-1 is `2dc72797acbc1b63fc16a11c4ac393605f453754`, identified by the [official 26.2 metadata](https://piston-meta.mojang.com/v1/packages/987b91a95ae93b3bb78cc14d6e0bbd31bad08d59/26.2.json). Symbol citations below refer to this [official 26.2 artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar). Fabric's [26.2 loot-table generation guide](https://docs.fabricmc.net/develop/data-generation/loot-tables) also demonstrates the chest context and describes conditions and functions, but does not establish offline reward semantics.

## Native context requirements

`LootContextParamSets` registers these serialized context IDs. Requirements concern native context keys, separately from the `ServerLevel`, luck and random source used for evaluation.

| Context | Required keys | Optional keys |
| --- | --- | --- |
| `minecraft:empty` | None | None |
| `minecraft:chest` | `ORIGIN` | `THIS_ENTITY` |
| `minecraft:command` | `ORIGIN` | `THIS_ENTITY` |
| `minecraft:advancement_reward` | `THIS_ENTITY`, `ORIGIN` | None |
| `minecraft:generic` | `THIS_ENTITY`, `LAST_DAMAGE_PLAYER`, `DAMAGE_SOURCE`, `ATTACKING_ENTITY`, `DIRECT_ATTACKING_ENTITY`, `ORIGIN`, `BLOCK_STATE`, `BLOCK_ENTITY`, `TOOL`, `EXPLOSION_RADIUS`, `ADDITIONAL_COST_COMPONENT_ALLOWED` | None |

The serialized `generic` entry maps to `LootContextParamSets.ALL_PARAMS`. It is also `LootTable.DEFAULT_PARAM_SET`; it is not a special offline-recipient context. `THIS_ENTITY` is typed as an actual `Entity`, `LAST_DAMAGE_PLAYER` as `Player`, and `ORIGIN` as `Vec3`. A UUID is not an entity substitute. Sources: `LootContextParamSets` static initialization and its registered builder lambdas, `LootContextParams`, and `LootTable` static initialization in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

`LootParams.Builder.create` delegates to `ContextMap.Builder.create`, which rejects missing required keys and keys outside the chosen set. `LootParams` still contains a `ServerLevel` and a separate float luck value. `withLuck` assigns that value directly. The ordinary `LootTable.getRandomItems` methods consume the supplied parameters; they do not construct missing entities or choose an origin for the caller. These methods do not themselves enforce that the table's declared context equals the caller's selected context. Sources: those methods in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

## Random selection

`LootTable.getRandomItems(LootParams, RandomSource)` passes the supplied source through `LootContext.Builder.withOptionalRandomSource`. In `create`, a non-null supplied source takes precedence over the table's optional `random_sequence`. Without an explicit source, the builder uses `MinecraftServer.getRandomSequence` for a supplied sequence ID, otherwise the level's random source. The long-seed overload uses `withOptionalRandomSeed`: a nonzero seed creates a seeded source, while zero means no seed override. A caller supplying a `RandomSource` object can avoid that zero-sentinel interpretation. Sources: `LootTable.getRandomItems`, `LootContext.Builder.withOptionalRandomSource`, `withOptionalRandomSeed`, and `create` in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

Named sequences are mutable saved state. `RandomSequences.get` retains a sequence by identifier and returns a wrapper that marks it dirty when random values are consumed. Sequence initialization uses the configured salt and optional world-seed/sequence-ID inputs. `NestedLootTable.createItemStack` evaluates its nested table with the existing `LootContext`, sharing that context's random source rather than independently choosing the nested table's sequence. Sources: `RandomSequences`, `RandomSequences.DirtyMarkingRandomSource`, `RandomSequence`, and `NestedLootTable` in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

Inference: the API supports independent caller-owned random sources for separate evaluations. A fixed source or seed alone does not freeze player state, world state, table dependencies, or mod behavior, and is not a reward receipt or duplicate-prevention mechanism.

## Offline evaluation limits

Native `AdvancementRewards.grant` requires a `ServerPlayer`. It grants experience, builds `ADVANCEMENT_REWARD` parameters from that player and the player's current position, evaluates tables, inserts resulting items, and drops remaining items when insertion fails. It also supports recipe rewards and an optional command function, separate from loot-table item functions. This is a live-player grant routine, not an offline mailbox API. Source: `AdvancementRewards.grant` in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

Native tables can inspect more than the supplied scalar values:

- `LootItemEntityPropertyCondition.test` obtains an actual entity from the context and evaluates an entity predicate against the server level and origin. Omitting the entity does not provide a snapshot of an offline player.
- `WeatherCheck.test` reads the current level's rain and thunder. `TimeCheck.test` reads the current server clock. These dependencies are not represented as additional entity context keys.
- `CopyNameFunction.run` obtains its source from a context argument and reads that object's name.
- `ExplorationMapFunction.run` searches the server level for a structure and creates a map. `MapItem.createNewSavedData` allocates a map ID and writes map saved data. The function declares only `ORIGIN` through `getReferencedContextParams`.

Sources: these exact methods in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

`ValidationContext.validateContextUsage` compares each component's reported referenced keys with the context's allowed keys and reports unsupported ones. A chest context permits `THIS_ENTITY` even when this particular caller omits it. Normal context validation also does not prove absence of world access, side effects, or unreported dependencies in extension code. Source: `ValidationContext.validateContextUsage` and `LootContextUser.validate` in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

Integration inference: a verified subset of chest-context tables can be evaluated with a real server level, an explicitly supplied origin, zero luck and no player or combat inputs, without inventing a player entity. Enforcing that subset requires checking the actual supplied inputs and supported transitive tables, conditions, functions and providers. Accepting the `chest` label or passing vanilla context validation alone is insufficient. Neither this research nor Fabric's general loot API proves arbitrary native/mod tables safe for offline recipients, independent of current world state, bounded in cost, or free of side effects. No arena origin or recipient-specific entity state is inferred here.

## Inventory, experience and saving

`Player.addItem` mutates the player's `Inventory`; `Player.giveExperiencePoints` mutates score and experience state. `Player.addAdditionalSaveData` serializes inventory and `XpP`, `XpLevel` and `XpTotal`. `PlayerList.remove` saves the disconnecting player and then removes its live world/list/map entries. Saved player data can be loaded separately by `NameAndId`; it does not become an active `ServerPlayer` merely because the UUID is known. Sources: those methods and `PlayerDataStorage.load` in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

`PlayerDataStorage.save` serializes a player to a temporary compressed file and replaces the UUID data file with a backup path. Its inspected API returns void and logs save exceptions. `PlayerList.save` separately invokes player-data, statistics and advancement saves. Inference: ordinary inventory mutation or an XP grant is not proof that a separate Conclave entitlement record and Minecraft's player data were durably committed together. These inspected methods provide no shared transaction with an external reward ledger. Source: `PlayerDataStorage.save` and `PlayerList.save` in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

No runtime integration, offline reward grant, crash test, table-subset validator or deterministic replay test was performed. This note selects no Conclave evaluation time, context policy, delivery workflow or persistence design.

## Item payload and experience bounds

Additional inspection on 2026-09-26 distinguished serialization limits from normal gameplay validation. This section selects no Conclave item schema or numerical budget.

`ItemStack` and `ItemStackTemplate` serialize a nonempty stack's `count` through an integer codec bounded from 1 to 99, with default 1. That is not permission to put 99 of every item in one stack. `ItemInstance.getMaxStackSize` reads the resolved `MAX_STACK_SIZE` component. `ItemStack.validateStrict` separately rejects a count above that maximum, and validates component combinations, including the incompatibility of `MAX_DAMAGE` with a maximum stack size greater than one. The `MAX_STACK_SIZE` component itself has a persistent codec bounded from 1 to 99. `ItemStack.setCount` directly assigns its integer and does not enforce those checks. Sources: `ItemStack.lambda$static$1`, `validateStrict`, `validateComponents`, `setCount`, `ItemStackTemplate.lambda$static$0`, `ItemInstance.getMaxStackSize`, and `DataComponents.lambda$static$1` in the [26.2 artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar). Mojang's [1.20.5 release notes](https://feedback.minecraft.net/hc/en-us/articles/26136167989005-Minecraft-Java-Edition-1-20-5-Armored-Paws) also document the component range; the current values above were checked in 26.2.

Inference: a reward's total quantity and the count of each actual native stack are different values. A total spanning multiple stacks cannot be represented as one oversized native stack merely because a setter accepts it. The native 1-to-99 codec range does not establish Conclave's total item quantity or storage budget. Invalid `ItemStackTemplate` creation can log a warning and return `ItemStack.EMPTY`, so successful method return alone is not proof that a requested reward exists. Source: `ItemStackTemplate.validate` in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

Enchantment references use the native enchantment registry through `Enchantment.CODEC`, a `RegistryFixedCodec`. `ItemEnchantments.CODEC` stores a map of enchantment holders to integer levels from 1 to 255. Each enchantment definition independently supplies `max_level`, itself bounded from 1 to 255, supported item references and an exclusive set. `Enchantment.canEnchant` tests membership in supported items. `Enchantment.areCompatible` checks distinct identity and both exclusive sets. Native `EnchantCommand.enchant` checks the selected level against `getMaxLevel`, item applicability and compatibility before applying it. Sources: `Enchantment` static initialization, `Enchantment.EnchantmentDefinition` codec, `ItemEnchantments` static initialization, and those methods in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

The low-level mutation path is more permissive. `ItemEnchantments.Mutable.set` removes nonpositive levels and clamps positive levels to 255; `upgrade` also caps levels at 255. These methods do not enforce the selected enchantment's normal maximum, item applicability or pairwise exclusivity. `ItemStack.enchant` uses `EnchantmentHelper.updateEnchantments`, which chooses `STORED_ENCHANTMENTS` for an enchanted book and `ENCHANTMENTS` otherwise. If the selected component is absent, that helper returns an empty result without mutation. Inference: schema validation cannot rely on calling this helper and assuming it rejected every unsupported request. Sources: these methods in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

The standard `EnchantmentHelper.enchantItem` path for a plain `minecraft:book` generates enchantments, creates a `minecraft:enchanted_book` stack and applies the results through `ItemStack.enchant`, which selects stored enchantments as above. `getAvailableEnchantmentResults` accepts a candidate when it is a primary item for that enchantment or when the input is a plain book. It searches levels from the enchantment's maximum down to its minimum, using the level's cost bounds. `selectEnchantment` filters further selections through `filterCompatibleEnchantments`, which calls `Enchantment.areCompatible`. `EnchantmentHelper.isEnchantmentCompatible` separately checks one candidate against a collection. Inference: ordinary book generation preserves native level and compatibility rules but has an explicit book exception to ordinary item suitability. Calling `canEnchant` on an enchanted book as though its stored enchantments were applied equipment effects would not reproduce that path. This does not establish that every loot function, provider or direct component mutation applies the same restrictions. Sources: these exact methods and `lambda$getAvailableEnchantmentResults$0/1` in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

`ServerPlayer.giveExperiencePoints(int)` treats zero as a no-op and otherwise delegates to `Player.giveExperiencePoints`. The latter adds the amount to score, converts points into float experience progress and adjusts levels in a loop. It computes `totalExperience + amount` with integer addition before calling `Mth.clamp` with bounds 0 and 2,147,483,647. Inference from that bytecode: a positive addition that overflows the signed integer can become negative before the clamp; this is not safe saturation arithmetic. The accepted integer input type therefore does not establish a safe universal positive grant maximum. Existing player state, accumulated totals, float rounding and level-adjustment work require their own verified delivery bounds. Sources: `ServerPlayer.giveExperiencePoints`, `Player.giveExperiencePoints` and `Player.getXpNeededForNextLevel` in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar). No large-XP runtime behavior was tested.

### Existing Conclave item syntax

At the inspection before Q256-Q257 were accepted, [Q144](npc-stats-and-combat.md#q144-typed-equipment) accepts a concise registered item ID and a configured item form capable of counts, enchantments and supported typed properties. It does not fix count defaults, exact enchantment map/list shape or normal-versus-out-of-range enchantment policy. [Q231](model-lighting-bounds-and-item-appearance.md) explicitly accepts `item` and optional `item_model` in the configured form and requires `item` for equipment. No accepted real-item `name`, `custom_name`, `item_name` or `lore` field schema was found; existing reward-entry names and presentation text do not implicitly define those native item properties. [Completion reward payloads](completion-rewards-and-test-policy.md) still describe exact item/XP shapes as dependent decisions. This records documentation state, not a proposed schema.

[Q256-Q257](fixed-reward-items-and-enchantments.md) subsequently accepted fixed item/XP fields and the explicit-enchantment map. This does not change the native evidence or establish an implemented adapter.
