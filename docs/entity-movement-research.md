# Native dimension changes and loss of entity simulation

Checked 2026-09-27 for Minecraft Java 26.2. This is factual research, not a Conclave movement policy or an implemented adapter. It adds no arena walls, automatic return behavior or moving chunk-ticket policy.

## Primary evidence

Native methods were inspected in the cached [official 26.2 client artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar), SHA-1 `2dc72797acbc1b63fc16a11c4ac393605f453754`, identified by [Mojang's metadata](https://piston-meta.mojang.com/v1/packages/987b91a95ae93b3bb78cc14d6e0bbd31bad08d59/26.2.json). The artifact contains named common and server classes. Fabric sources below are pinned to commit `0ec1d58582bd816012a8f9f1617eb4dfdeda1e93` from the previously inspected 26.2 source line.

Existing [arena readiness](arena-placement-and-admission.md#q107-keeping-an-active-arena-available) and [NPC lifecycle research](npc-combat-research.md) already distinguish bounded retained simulation from ordinary despawn, death and cleanup. This note does not reopen those contracts.

## Cross-dimension identity

For entities using the ordinary inherited path, `Entity.teleportCrossDimension` creates a destination entity of the same type with `EntitySpawnReason.DIMENSION_TRAVEL`, calls `newEntity.restoreFrom(original)`, removes the original through `removeAfterChangingDimensions`, places the new entity and adds it to the destination level. It returns the new object. The inspected `LivingEntity` and `Mob` classes do not override this teleport method. Individual subclasses and other mods can still supply different behavior. Source: these classes and methods in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

`Entity.restoreFrom` transfers state through `saveWithoutId` followed by `load`, then copies portal state. The save contains `UUID`; loading restores that UUID and its string representation. Thus the ordinary non-player transfer changes the object while retaining the UUID. Arbitrary unsaved Kotlin fields or an external map keyed only by the original object are not copied by this native serialization operation. The latter is an integration inference, not a statement about any implemented Conclave state store. Sources: `Entity.restoreFrom`, `saveWithoutId`, `load` and `lambda$load$0` in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

`ServerPlayer.teleport` uses a different cross-dimension path. It removes the same player from the origin with `CHANGED_DIMENSION`, clears its removed flag, changes its server level and adds that same object to the destination. It returns `this`. Player respawn is a separate case: Fabric explicitly documents that a respawn into another level creates a replacement player, and directs consumers needing the old object to `ServerPlayerEvents.AFTER_RESPAWN`. Sources: `ServerPlayer.teleport` in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar) and [ServerEntityLevelChangeEvents](https://github.com/FabricMC/fabric/blob/0ec1d58582bd816012a8f9f1617eb4dfdeda1e93/fabric-entity-events-v1/src/main/java/net/fabricmc/fabric/api/entity/event/v1/ServerEntityLevelChangeEvents.java).

Same-dimension teleport uses `Entity.teleportSameDimension`, updates the existing object and returns it. The cross-dimension routine also processes passengers separately and can return null if destination entity creation fails. These methods do not establish an atomic transfer of every passenger and every mod-owned attachment. Source: these exact methods in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

## Removal and simulation are separate observations

The native removal reasons have these flags. The flags describe native destruction/save handling, not Conclave gameplay outcomes.

| Removal reason | `shouldDestroy` | `shouldSave` |
| --- | --- | --- |
| `KILLED` | true | false |
| `DISCARDED` | true | false |
| `UNLOADED_TO_CHUNK` | false | true |
| `UNLOADED_WITH_PLAYER` | false | false |
| `CHANGED_DIMENSION` | false | false |

`Entity.removeAfterChangingDimensions` sets `CHANGED_DIMENSION`. `PersistentEntitySectionManager.unloadEntity` sets `UNLOADED_TO_CHUNK`. `Entity.setRemoved` calls the level removal callback and `onRemoval`; removal itself is not a call to `LivingEntity.die`. Sources: these methods and `Entity.RemovalReason` initialization/accessors in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar). As the prior [creeper research](npc-combat-research.md) demonstrates, `DISCARDED` can also accompany native self-destruction, so a reason alone is not a universal terminal-outcome classifier.

`Visibility` separately represents `HIDDEN`, `TRACKED` and `TICKING`. `TRACKED` is accessible but not ticking. `Visibility.fromFullChunkStatus` maps entity-ticking chunks to `TICKING`, full or block-ticking chunks to `TRACKED`, and inaccessible chunks to `HIDDEN`. `PersistentEntitySectionManager.Callback.onMove` updates the entity's section and its effective status. Its `updateStatus` can call `stopTicking` independently of `stopTracking`. Chunk status changes can make the same transition without entity movement. Sources: `Visibility`, `PersistentEntitySectionManager.Callback.onMove` and `updateStatus`, and `PersistentEntitySectionManager.updateChunkStatus` in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

`ServerLevel.EntityCallbacks.onTickingEnd` removes the entity from `entityTickList`; it does not kill or remove the entity. `PersistentEntitySectionManager.isLoaded(UUID)` checks the known UUID set, which is not an entity-ticking predicate. `ServerLevel.isPositionEntityTicking` checks both the entity manager's position status and `DistanceManager.inEntityTickingRange`. The actual entity tick loop also checks removed state, native tick freezing and entity-ticking range for non-player entities, and handles passengers through a separate path. Sources: these methods, `PersistentEntitySectionManager.canPositionTick`, and `ServerLevel.lambda$tick$0` in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

Integration inference: a present entity reference or loaded UUID does not prove continued simulation. An owned entity can stop ticking without dying and before a later disk unload. The inspected readiness queries are useful observations, not a guarantee that every entity has executed its next tick. Native freezing, passengers and version-specific integration still matter.

## Fabric observations and their limits

The 26.2 API is named `ServerEntityLevelChangeEvents`. `AFTER_ENTITY_CHANGE_LEVEL` supplies the original entity, replacement entity, origin and destination; it excludes players. `AFTER_PLAYER_CHANGE_LEVEL` supplies the current player plus origin and destination and also covers the documented cross-level respawn case. These are after-events, not cancellable pre-transfer events. Sources: [the event API](https://github.com/FabricMC/fabric/blob/0ec1d58582bd816012a8f9f1617eb4dfdeda1e93/fabric-entity-events-v1/src/main/java/net/fabricmc/fabric/api/entity/event/v1/ServerEntityLevelChangeEvents.java), [EntityMixin](https://github.com/FabricMC/fabric/blob/0ec1d58582bd816012a8f9f1617eb4dfdeda1e93/fabric-entity-events-v1/src/main/java/net/fabricmc/fabric/mixin/entity/event/EntityMixin.java) and [ServerPlayerMixin](https://github.com/FabricMC/fabric/blob/0ec1d58582bd816012a8f9f1617eb4dfdeda1e93/fabric-entity-events-v1/src/main/java/net/fabricmc/fabric/mixin/entity/event/ServerPlayerMixin.java).

Fabric invokes its non-player after-event only after `teleportCrossDimension` returns a non-null destination entity. Native old-object removal has already occurred by then. The player event is injected at the tail of `triggerDimensionChangeTriggers`, after native destination placement in the inspected teleport path. Integration inference: a consumer must correlate transfer observations instead of treating origin removal as proof of death or a permanently missing NPC. These callbacks alone cannot veto a transition before native changes occur, and do not prove that arbitrary mod teleport code follows the instrumented path. Sources: the mixins above and the native teleport methods.

`ServerEntityEvents.ENTITY_LOAD` and `ENTITY_UNLOAD` expose an entity and level. The pinned implementation injects them at `ServerLevel.EntityCallbacks.onTrackingStart` tail and `onTrackingEnd` head. They are server tracking-lifecycle notifications, not per-player network tracking events, death notifications or exact entity-ticking transitions. Loss of server accessibility can invoke tracking-end without native death. A `TICKING` to `TRACKED` transition can stop simulation while retaining tracking. Sources: [ServerEntityEvents](https://github.com/FabricMC/fabric/blob/0ec1d58582bd816012a8f9f1617eb4dfdeda1e93/fabric-lifecycle-events-v1/src/main/java/net/fabricmc/fabric/api/event/lifecycle/v1/ServerEntityEvents.java), [its callback mixin](https://github.com/FabricMC/fabric/blob/0ec1d58582bd816012a8f9f1617eb4dfdeda1e93/fabric-lifecycle-events-v1/src/main/java/net/fabricmc/fabric/mixin/event/lifecycle/ServerLevelEntityCallbacksMixin.java) and the native status methods above.

`ServerChunkEvents.FULL_CHUNK_STATUS_CHANGE` supplies old/new full status before actual ticking behavior finishes aligning. Its documentation warns that entities may not yet be accessible and the corresponding status future may not be complete. `CHUNK_UNLOAD` is later than first loss of accessibility in ordinary cases. Consequently, neither chunk load/unload alone nor this transitional callback alone proves a completed entity-readiness boundary. Source: [ServerChunkEvents](https://github.com/FabricMC/fabric/blob/0ec1d58582bd816012a8f9f1617eb4dfdeda1e93/fabric-lifecycle-events-v1/src/main/java/net/fabricmc/fabric/api/event/lifecycle/v1/ServerChunkEvents.java).

## Unverified integration boundaries

No runtime transfer, portal, passenger, unload/reload or cleanup test was run. No complete Conclave ownership handoff, before-stop-ticking interception, destination readiness check or durable cleanup record is implemented. This research does not prove that Fabric's public callbacks alone satisfy every required boundary, that object-local mod state follows a native clone, or that another mod cannot bypass the observed paths. It selects no participant policy, owned-NPC response, new ticket footprint or cross-dimension encounter support.
