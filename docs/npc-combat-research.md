# NPC attribute and combat research

Checked 2026-09-17 for Minecraft Java 26.2 and Fabric. These are source findings for the design interview, not accepted Conclave gameplay policy. No Conclave combat integration has been implemented or tested live.

**Native `minecraft:max_health` is capped at 1,024 health points, or 512 hearts.** Setting a larger base value or adding modifiers does not bypass that cap. Supporting larger boss health requires additional implementation beyond ordinary attribute assignment.

The native findings below come from disassembling Mojang's [official 26.2 client artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar), which includes common and integrated-server classes. Its SHA-1 was verified against the artifact URL and [official version metadata](https://piston-meta.mojang.com/v1/packages/987b91a95ae93b3bb78cc14d6e0bbd31bad08d59/26.2.json). Method names identify the inspected implementation; this was static inspection, not a running-server test.

## Native attribute meanings and limits

The table records the registered `RangedAttribute` bounds in `Attributes`, not proposed Conclave authoring limits or the default values of each entity type. `AttributeInstance.calculateValue` applies modifiers and then sanitizes the result against these bounds.

| Attribute | Native range | Meaning and limitation |
| --- | --- | --- |
| `minecraft:max_health` | 1 to 1,024 | Maximum ordinary health in health points. Two points equal one heart. Current health is separate. |
| `minecraft:attack_damage` | 0 to 2,048 | Input to ordinary mob melee damage. Equipment, enchantments, the attack implementation, difficulty, and victim defenses can change the result. |
| `minecraft:movement_speed` | 0 to 1,024 | Movement-control input. It is not a universal blocks-per-second value. |
| `minecraft:armor` | 0 to 30 | Armor points used by vanilla mitigation, not a percentage or a flat number of damage points removed. |
| `minecraft:armor_toughness` | 0 to 20 | Separate input to armor's response to stronger hits. |
| `minecraft:knockback_resistance` | -2 to 1 | Ordinary `LivingEntity.knockback` multiplies incoming strength by `1 - resistance`. Zero leaves strength unchanged, one prevents that knockback, and negative values amplify it. |
| `minecraft:scale` | 0.0625 to 16 | Physical scale of supported living entities. Dimensions change as well as the intended presentation. |

Source: `Attributes`, `RangedAttribute.sanitizeValue`, `AttributeInstance.calculateValue`, `LivingEntity.knockback`, and `CombatRules.getDamageAfterAbsorb` in the [26.2 artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar). Fabric explicitly demonstrates five damage points as 2.5 hearts in its [damage-type guide](https://docs.fabricmc.net/develop/entities/damage-types).

Explosion knockback has a separate `minecraft:explosion_knockback_resistance` attribute, ranging from zero to one, read by `ServerExplosion.hurtEntities`. Ordinary knockback resistance does not promise immunity to explosions, collisions, or an implementation that directly changes velocity.

`LivingEntity.getDimensions` normally scales its default dimensions, and a scale-attribute update refreshes dimensions. Entity-specific exceptions remain: the inspected `Shulker.sanitizeScale` caps effective scale at three, while `EnderDragon.sanitizeScale` returns one. Sleeping dimensions are also handled separately. Scale is therefore an adapter capability with placement and collision consequences. Source: the named methods in the [26.2 artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

## Base values, speed, and larger health pools

Fabric exposes default attributes for living entity types, while vanilla exposes each instance's base and calculated values. Attributes must be supported by the entity to be useful. A readable speed multiplier can be translated into the supported base entity type's movement value, with `1.0` retaining that baseline. That translation is a Conclave implementation choice. Native `MoveControl.tick` further multiplies the movement attribute by its current movement-speed modifier; terrain, effects, and navigation still affect travel. `FlyingMoveControl` uses `FLYING_SPEED` while airborne, so changing only `MOVEMENT_SPEED` does not establish a universal flying-speed control. Sources: [Fabric attributes](https://docs.fabricmc.net/develop/entities/attributes), [Fabric default-attribute registry](https://maven.fabricmc.net/docs/fabric-api-0.152.0+26.2/net/fabricmc/fabric/api/object/builder/v1/entity/FabricDefaultAttributeRegistry.html), and the named classes in the [26.2 artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

No documented Fabric 26.2 facility for increasing the built-in maximum-health range per entity was found in this bounded check. `RangedAttribute` stores final minimum and maximum fields; its API has getters but no range setter. `LivingEntity.getMaxHealth` is final and reads `Attributes.MAX_HEALTH`. Fabric's default-attribute registry supplies defaults for entity types, and its custom-attribute guide registers new attributes. Neither changes vanilla health's clamp. A new custom attribute alone will not become vanilla health. Source: the [Fabric attribute guide](https://docs.fabricmc.net/develop/entities/attributes), [default-attribute registry](https://maven.fabricmc.net/docs/fabric-api-0.152.0+26.2/net/fabricmc/fabric/api/object/builder/v1/entity/FabricDefaultAttributeRegistry.html), and the inspected native classes.

Implementation inference: more than 1,024 native health points would require custom mixins or attribute handling, or a separate logical health pool with explicit combat integration. Changing the shared registered attribute's range would affect more than one NPC unless additional scoping were implemented. This note does not select an approach or promise compatibility with other combat mods.

## Melee, projectiles, and explosions

`Mob.doHurtTarget` reads `ATTACK_DAMAGE`, applies weapon/enchantment adjustments, and calls the victim's `hurtServer`. Native skeleton arrows follow `ProjectileUtil.getMobArrow` and `AbstractArrow.setBaseDamageFromMob`; their impact damage uses the arrow's own base damage and velocity, with further adjustments. `ExplosionDamageCalculator.getEntityDamageAmount` uses explosion radius, distance, and exposure. These paths do not make the shooter's melee attribute a general ranged or explosion multiplier. Modded entities can implement other behavior. Source: the named methods in the [26.2 artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

A YAML `damage` property therefore needs an advertised meaning for each supported NPC adapter. A separately authored damage action can pass its own health-point amount to `hurtServer`; the native `attack_damage` attribute's upper bound is not a general cap on that method's amount argument. Neither operation promises that the target loses exactly the authored number of health points.

## Damage processing and direct health assignment

Fabric's documented entry point is `entity.hurtServer(serverLevel, damageSource, amount)`. Damage types are server data definitions, with tags controlling properties such as bypassing armor or effects. `DamageSource` also supplies attribution. In vanilla, `LivingEntity.hurtServer` checks immunity and death state, processes item blocking and hurt cooldowns, and reaches armor, resistance, enchantment, and absorption handling before subtracting health. It also participates in combat tracking, damage feedback, totem protection, and death processing. Player damage may scale with difficulty according to the damage source. Sources: [Fabric damage types](https://docs.fabricmc.net/develop/entities/damage-types) and `LivingEntity.hurtServer`, `actuallyHurt`, `Player.hurtServer`, and `Entity.isInvulnerableToBase` in the [26.2 artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

Hurt cooldowns are distinct from an entity's invulnerable flag. During the ordinary cooldown comparison, an equal or weaker repeated hit can be rejected, while a stronger hit applies only the excess over the previous hit. A damage-type tag can bypass that comparison. Armor bypass does not itself mean every other defense is bypassed. The native invulnerable flag also has exceptions, including designated bypass damage and creative-player attacks. An absolute Conclave vulnerability contract would need explicit implementation and verification.

`setHealth` only writes health clamped to zero through current maximum health. Calling `setHealth(currentHealth - amount)` skips the normal damage-processing entry point and its attribution and mitigation. It must not be described as equivalent to a vanilla damage action. Source: `LivingEntity.setHealth` and the damage methods above.

Fabric provides cancellable `ALLOW_DAMAGE`, `ALLOW_DEATH`, and observation events. Its `AFTER_DAMAGE` amount is explicitly before armor/enchantment reduction and the event does not fire for lethal damage. It is not a ready-made final-health-loss event. Source: [Fabric 26.2 living-entity events](https://maven.fabricmc.net/docs/fabric-api-0.152.0+26.2/net/fabricmc/fabric/api/entity/event/v1/ServerLivingEntityEvents.html).

## Healing and maximum-health changes

`LivingEntity.heal(amount)` adds the amount only when current health is above zero, then calls `setHealth`, which clamps to the current maximum. Ordinary positive healing therefore does not resurrect a dead entity or add absorption hearts. Native healing's argument is not validated as a positive authoring value; a typed Conclave action would need its own finite-value validation.

When native dirty-attribute processing observes a maximum-health change, it reduces current health if current health exceeds the new maximum. Increasing maximum health does not heal, fill the new capacity, or preserve the old health percentage automatically. Initial health, healing, and runtime maximum-health changes need separate semantics in the schema. Source: `LivingEntity.heal`, `setHealth`, `refreshDirtyAttributes`, and `onAttributeUpdated` in the [26.2 artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

## Q141 follow-up: raising the health ceiling

**Yes. The 1,024 limit is an attribute clamp that mod code can change, not a limit of the health save field or network encoding.** The following comparison records the engineering alternatives that informed the accepted Q146 decision. It is not a live compatibility result.

There is current implementation precedent. AttributeFix's maintainer-owned 26.2 branch at commit `d8b2b744aa9dd60034fda9dd59afbbadb2725d13` uses a Mixin `@Accessor` with `@Mutable` to change `RangedAttribute.maxValue`. Its default configuration raises `minecraft:max_health` to **1,000,000**, and its Fabric entry points initialize the change on dedicated servers and clients. This establishes a concrete technique for this version, not a recommendation to install the dependency or copy all its attribute changes. Sources: [range configuration](https://github.com/Darkhax-Minecraft/AttributeFix/blob/d8b2b744aa9dd60034fda9dd59afbbadb2725d13/common/src/main/java/net/darkhax/attributefix/common/impl/config/RangeConfig.java), [range accessor](https://github.com/Darkhax-Minecraft/AttributeFix/blob/d8b2b744aa9dd60034fda9dd59afbbadb2725d13/common/src/main/java/net/darkhax/attributefix/common/mixin/AccessorRangedAttribute.java), [server initializer](https://github.com/Darkhax-Minecraft/AttributeFix/blob/d8b2b744aa9dd60034fda9dd59afbbadb2725d13/fabric/src/main/java/net/darkhax/attributefix/fabric/AttributeFixFabric.java), and [client initializer](https://github.com/Darkhax-Minecraft/AttributeFix/blob/d8b2b744aa9dd60034fda9dd59afbbadb2725d13/fabric/src/main/java/net/darkhax/attributefix/fabric/AttributeFixFabricClient.java). Fabric documents [mutable accessor setters for final fields](https://docs.fabricmc.net/develop/mixins/accessors#setting-final-fields).

| Approach | Engineering assessment | Scope and extra work |
| --- | --- | --- |
| Raise only the shared `MAX_HEALTH` ceiling | Simplest evidenced implementation. Keep the native health, damage, healing, death, save, and synchronization paths. Leave default health values and other attributes unchanged. | The higher ceiling becomes available to every entity using that registered attribute, including players and other mods. This does not automatically give those entities more health, but existing values or modifiers previously clipped at 1,024 may become effective. |
| Extend only marked Conclave NPC attribute instances | Plausible scope-preserving implementation. Intercept the final sanitization of the owned NPC's `MAX_HEALTH` instance while retaining native modifier calculation and health processing. | Custom implementation, not a Fabric feature or verified prototype. Attribute instances have no built-in NPC-owner field. Ownership must be established on both sides before evaluation and before saved health is clamped; changes must invalidate cached values. Ordinary attribute packets and saves do not carry that ownership marker. |
| Maintain separate logical health | Can use a separate numeric representation and range. | Requires reconciliation with native damage, healing, absorption, totems, death, other mods, persistence, and the HUD. It creates substantially more integration work than lifting the native clamp. |

Engineering assessment: a narrow shared-ceiling change is the simplest evidenced approach when its broader availability is acceptable. A requirement that only Conclave NPCs may exceed the native cap would instead require prototyping the instance-scoped approach. A separate health pool is not justified by the 1,024 limit alone. The user accepted the shared-ceiling tradeoff in Q146.

The accepted [Q146 contract](npc-stats-and-combat.md#q146-increased-native-health-ceiling) is an internal `max_health`-only startup extension on both sides, with Conclave-authored health limited to 1,000,000. Preserve a higher compatible ceiling supplied by another mod instead of lowering it; Conclave's authoring validation remains separate from that shared runtime ceiling. Keep existing defaults and the native health pool. Implementation testing remains outstanding.

The 26.2 artifact confirms the transport and persistence details. `LivingEntity.addAdditionalSaveData` writes current health as a float; `AttributeInstance.Packed` stores attribute base values with `Codec.DOUBLE`. Loading restores attributes before calling `setHealth` on the saved health. `ClientboundUpdateAttributesPacket.AttributeSnapshot` sends the attribute identifier, double base value, and modifiers. `ClientPacketListener.handleUpdateAttributes` reconstructs the local attribute instance; its range is not included in that packet. Current health uses the float entity-data serializer. No independent 1,024 cap appears in these inspected codecs. Source: the named methods/classes in the [26.2 artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

Consequently, the same effective ceiling must be available on server and client. Initialize it before entity loading or cached calculations, and test reconnects and tracking changes. Loading saved high-health entities without the extension can clamp their health back to the native maximum. An instance-scoped implementation must restore and synchronize its ownership state at the right time; merely adding a marker after normal loading is insufficient. Exact lifecycle hooks, interaction with other attribute-changing mods, and migration behavior remain implementation work.

**A finite 1,000,000-HP authoring ceiling is a reasonable candidate, not a precision-free value.** Java floats have 24 significant binary bits. At 1,000,000 HP, adjacent representable values are 0.0625 HP apart. Integer and half-point health values remain representable, but small fractional damage/healing can round away; a 0.01-HP subtraction at that health leaves the float unchanged. At one billion HP, spacing is 64 HP and even a one-point hit can disappear numerically. These values were checked with binary32 arithmetic, not an in-game test. Sources: [Java 25 float precision](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Float.html#PRECISION) and [ULP definition](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Math.html#ulp(float)).

Reject non-finite authored values and validate the chosen ceiling, including the intended treatment of modifiers. Before promising support, test high-health spawn/load/save, joining clients, small and lethal damage, healing, temporary max-health modifiers, and native combat integrations. The source evidence supports feasibility; none of these Conclave integration tests has run.

## Q147-Q151 source facts: damage kinds, reloads, and immunity

Checked against the same official 26.2 artifact and Fabric's 26.2 branch at commit `0ec1d58582bd816012a8f9f1617eb4dfdeda1e93`. These additions informed the accepted Q147-Q151 contracts. They are not implementation tests.

### Native damage kinds and attribution

The shipped definitions and tags establish the following defaults. External data packs can change tag membership.

| Native identifier | Armor and ordinary shield | Other relevant defaults |
| --- | --- | --- |
| `minecraft:generic` | Bypasses both | Not an armor-respecting physical default. Exhaustion is zero. |
| `minecraft:magic` | Bypasses both | Does not automatically bypass Resistance, protective enchantments, absorption, or totems. Exhaustion is zero. |
| `minecraft:on_fire` | Bypasses both | Tagged as fire; fire immunity/Fire Resistance applies. Uses burning feedback, with zero exhaustion. The damage type itself does not ignite or schedule burning. |
| `minecraft:mob_attack` | Eligible for normal armor and shield processing | Exhaustion is 0.1. Native helper supplies the attacking mob. |
| `minecraft:player_attack` | Eligible for normal armor and shield processing | Exhaustion is 0.1. Native helper supplies the attacking player. |

All five definitions use `when_caused_by_living_non_player` difficulty scaling. The actual causing entity determines whether that condition holds; choosing an identifier alone does not provide attribution. None of these five is in the shipped invulnerability-bypass tag. Source: `data/minecraft/damage_type/`, `data/minecraft/tags/damage_type/`, `DamageSources`, and `DamageSource.scalesWithDifficulty` in the [26.2 artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

`DamageSource` distinguishes the direct entity, such as a projectile, from the causing entity, such as its shooter. It can alternatively carry an explicit origin position. `getSourcePosition` uses that explicit position or the direct entity's current position. Native item blocking checks active item use, its blocking delay, bypass rules, projectile piercing, and the incoming angle. With no source position, the blocking calculation uses an angle of pi; the ordinary shield's 90-degree rule therefore does not block it. A valid damage kind does not guarantee a shield-blockable hit. Sources: `DamageSource`, `LivingEntity.applyItemBlocking`, `getItemBlockingWith`, `BlocksAttacks.DamageReduction`, and the shield component initializer in the [26.2 artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

The accepted small built-in `conclave:physical` type fits the normal startup mechanism: bundle `data/conclave/damage_type/physical.json` with the installed mod, resolve its registered holder, use `scaling: "never"`, and do not place it in bypass tags. That retains the native defenses described above, subject to attribution, origin, and current external tags. It does not require an arbitrary damage-type authoring language. Sources: [Fabric's damage-type guide](https://docs.fabricmc.net/develop/entities/damage-types) and [Mojang's damage-type field definitions](https://www.minecraft.net/en-us/article/minecraft-java-edition-1-19-4). This establishes feasibility; [Q147](combat-rules-and-health.md#q147-damage-types-and-the-physical-default) records the accepted design choice.

### What vanilla reload actually retains

In 26.2, `RegistryDataLoader` includes `DAMAGE_TYPE` in the startup `WORLDGEN_REGISTRIES` and synchronized registries. Ordinary `MinecraftServer.reloadResources` reloads tags for existing registries and reloadable resources; `ReloadableServerRegistries.reload` rebuilds loot-data registries, not damage-type entries. Thus ordinary `/reload` retains the current damage-type definitions and registered holders, while successful tag application changes those holders' tag membership. Changes to damage-type JSON entries require a new registry-loading lifecycle, normally a server/world restart, under this inspected vanilla path.

`MappedRegistry` refreshes tags in existing `Holder.Reference` objects. `DamageSource.is(tag)` consults its holder each time. An old captured `DamageSource` or holder therefore remains a reference to live tags, not a snapshot of mitigation rules. A copied `DamageType` in a direct holder is not a substitute: `Holder.Direct.is(tag)` always returns false. Across a new server/registry lifecycle, resolve the stored identifier against that lifecycle's registry rather than treating an old holder as portable. Sources: the named classes in the [26.2 artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

Consequently, pinning a Conclave definition revision can pin its selected damage identifier, but cannot by itself pin native tags. The design must state how external data changes affect active attempts. A successful-reload technical stop before relevant changes become live is plausible, but requires a Conclave hook and dependency tracking.

The accepted [Q148 contract](combat-rules-and-health.md#q148-external-gameplay-data-reloads) instead rejects a conflicting reload before application and keeps attempts running. The pre-mutation point described below is relevant to either approach, but rejection also needs verified candidate disposal and failure reporting. Neither behavior is supplied by the existing Fabric notifications or has been tested here.

Fabric's `START_DATA_PACK_RELOAD` fires at reload entry, before preparation succeeds. `END_DATA_PACK_RELOAD` runs after the returned reload future completes, with a success flag. Both are notifications, with no cancellation or precommit callback. Vanilla does expose an implementation point: the success-only server-thread consumer in `MinecraftServer.reloadResources` first replaces resources and then applies pending tags. A version-specific mixin before its first mutation could stop affected attempts after preparation succeeds and before those tags change. Failed preparation would not reach this gate, so it need not stop attempts. A failure after the gate cannot promise rollback of already stopped attempts. Exact injection, identifying affected dependencies, admission during reload, and interactions with other reload listeners remain untested implementation work. Sources: [pinned Fabric reload-event declarations](https://github.com/FabricMC/fabric/blob/0ec1d58582bd816012a8f9f1617eb4dfdeda1e93/fabric-lifecycle-events-v1/src/main/java/net/fabricmc/fabric/api/event/lifecycle/v1/ServerLifecycleEvents.java), [pinned reload-event injection](https://github.com/FabricMC/fabric/blob/0ec1d58582bd816012a8f9f1617eb4dfdeda1e93/fabric-lifecycle-events-v1/src/main/java/net/fabricmc/fabric/mixin/event/lifecycle/MinecraftServerMixin.java), and the official artifact's reload methods.

### Explicit immunity and final damage observations

The native invulnerable flag has exceptions, including creative attackers and damage tagged `bypasses_invulnerability`. Fabric's `ALLOW_DAMAGE` can reject normal living-entity damage before blocking and mitigation, including sources that bypass the native flag. Its injection occurs after native early immunity, dead-state, and Fire Resistance checks. This is a suitable basis for the accepted Q149 NPC `vulnerable: false` contract, with adapter testing still required. It does not intercept direct health assignments, entity removal/discard, or an override that skips the normal damage method. Ordinary `/kill` on a living entity uses `hurtServer` with `generic_kill`, so an unconditional `ALLOW_DAMAGE` rejection can block that command too. Source: `Entity.isInvulnerableToBase`, `LivingEntity.kill`, and [pinned Fabric living-entity mixin](https://github.com/FabricMC/fabric/blob/0ec1d58582bd816012a8f9f1617eb4dfdeda1e93/fabric-entity-events-v1/src/main/java/net/fabricmc/fabric/mixin/entity/event/LivingEntityMixin.java).

For the inspected ordinary living-entity damage path, blocking and hurt-cooldown handling precede armor/effect mitigation, absorption consumption, and health subtraction. If health becomes lethal, Fabric's `ALLOW_DEATH` runs before vanilla checks totem protection. Cancelling death does not restore health by itself. If death remains allowed, a usable totem sets health to one and applies its effects; otherwise native death processing runs. `AFTER_DEATH` observes the death path. `AFTER_DAMAGE` runs at the end only if the entity is then alive, including a totem-saved entity; its amount arguments still omit armor/enchantment reduction. Sources: `LivingEntity.hurtServer`, `actuallyHurt`, `checkTotemDeathProtection`, and [pinned Fabric event definitions](https://github.com/FabricMC/fabric/blob/0ec1d58582bd816012a8f9f1617eb4dfdeda1e93/fabric-entity-events-v1/src/main/java/net/fabricmc/fabric/api/entity/event/v1/ServerLivingEntityEvents.java).

A Conclave event named final health loss therefore needs an explicit measurement point. Post-mitigation damage, absorption spent, health removed before rescue, and net health change after a totem or another mod intervenes are different quantities. No single existing Fabric callback supplies all of them, and neither a true return value from `hurtServer` nor `AFTER_DAMAGE.damageTaken` proves positive final health loss. Capturing these quantities and coordinating their order with defeat events is implementation work, not a guarantee supplied by selecting `damage.type`.

## Follow-up source facts: health floors and measured combat outcomes

This bounded inspection used the same official 26.2 artifact and pinned Fabric sources. The hook described here is an implementation inference; no Conclave mixin or live test has been built.

### A floor before native health subtraction

`LivingEntity.actuallyHurt` applies armor and effect mitigation, consumes absorption, and calculates the absorbed-damage statistic. It then checks whether the remaining damage is zero, records that amount with `CombatTracker.recordDamage(source, amount)`, and calls `setHealth(getHealth() - amount)`. This provides a narrow candidate hook **after absorption accounting and before the zero check and combat tracking**. Cap the remaining health-directed amount to the available health above the floor, and preserve the original `DamageSource`. Updating that shared amount lets tracking and subtraction agree; changing only the final setter would leave the combat record overstating the applied damage. Source: `LivingEntity.actuallyHurt` and `CombatTracker.recordDamage` in the [official 26.2 artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

Conceptually, the cap is `min(remainingDamage, max(0, currentHealth - floor))`. Applying it after absorption accounting avoids counting prevented health loss as absorption spent. A positive valid floor can prevent ordinary lethal health loss before the outer method reaches totem/death handling. Zero allowed loss takes the existing inner return, but the outer damage call may still produce hurt feedback, cooldown, knockback, and other hit behavior. A floor therefore does not automatically mean hit immunity. Exact float behavior at the threshold needs testing, especially with the accepted larger health ceiling. A cap also does not restore health that was already below the floor.

This hook has explicit limits. Direct `setHealth` calls and native maximum-health clamps bypass it; lowering maximum health below a floor cannot preserve that floor through the ordinary setter. Removal/discard bypasses damage entirely. `Player.actuallyHurt` has a separate override, and other mods can supply overrides that skip the common implementation, so each supported NPC adapter must verify its damage path. Conversely, ordinary living-entity `/kill` calls `hurtServer` with `generic_kill` and `Float.MAX_VALUE`: it reaches the normal damage path and is **not automatically exempt** from a floor. Sources: `LivingEntity.setHealth`, `onAttributeUpdated`, `kill`, and `Player.actuallyHurt` in the [26.2 artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

`ALLOW_DAMAGE` occurs before the final mitigation/absorption result is known. `ALLOW_DEATH` occurs after health subtraction and handles only lethal outcomes, so it cannot enforce a nonlethal floor and does not restore health on cancellation. Neither supplies the proposed amount-changing hook. Exact injection, compatibility with other damage mixins, and adapter coverage remain implementation work. Source: [pinned Fabric living-entity hooks](https://github.com/FabricMC/fabric/blob/0ec1d58582bd816012a8f9f1617eb4dfdeda1e93/fabric-entity-events-v1/src/main/java/net/fabricmc/fabric/mixin/entity/event/LivingEntityMixin.java).

### Quantities that authored events could distinguish

These are measurement boundaries, not selected event names or a schema:

| Quantity | Meaning and measurement boundary |
| --- | --- |
| Attack/action attempt | Observe the supported attack or action entry. A miss need not call victim damage; environmental damage need not originate from an attack. `ALLOW_DAMAGE` is not a universal attempt event because native early rejection can precede it. |
| Absorption spent | Measure absorption consumed by that damage calculation before rescue effects. Comparing absorption before and after the whole call can include absorption subsequently granted by a totem. |
| Actual health removed before rescue | Compare health immediately before and after the damage subtraction. This excludes absorption and captures the floor, native zero clamp, and float rounding. The incoming amount or combat-tracker amount alone can include lethal overkill. |
| Net health change after rescue | Compare health around the completed damage call, including totem or mod intervention. A hit removing the last 1 HP followed by a totem restoring 1 HP has zero net loss despite removing health. |
| Actual healing | For ordinary positive `heal`, measure the immediate health increase after its clamped setter; the requested amount can exceed the increase. Native `heal` has no source/cause argument, and direct health increases or totem restoration need not call it. Attribution requires action context or additional supported hooks. |

Sources: `LivingEntity.hurtServer`, `actuallyHurt`, `checkTotemDeathProtection`, `heal`, and `setHealth` in the [26.2 artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar), plus the [pinned Fabric hook locations](https://github.com/FabricMC/fabric/blob/0ec1d58582bd816012a8f9f1617eb4dfdeda1e93/fabric-entity-events-v1/src/main/java/net/fabricmc/fabric/mixin/entity/event/LivingEntityMixin.java). The earlier `AFTER_DAMAGE` caveat still applies. Correlating measurements within one call, nested damage, death/rescue ordering, and authored reactions needs explicit implementation; one end-of-call delta cannot recover every intermediate outcome.

### Attribution together with a separate damage origin

The full native `DamageSource(holder, directEntity, causingEntity, Vec3)` constructor stores all four values but is **private**. Public constructors support attributed entities or an explicit position separately. `getSourcePosition()` prefers the explicit position, then the direct entity's current position, then null; `sourcePositionRaw()` returns only the explicit position. A small installed-code adapter using a constructor invoker is plausible: Fabric documents invokers for inaccessible constructors. This could retain server attribution while using an authored location for native origin-sensitive checks. Sources: `DamageSource` in the [26.2 artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar) and [Fabric constructor invokers](https://docs.fabricmc.net/develop/mixins/accessors#method-invokers).

There is a client boundary: `ClientboundDamageEventPacket` carries entity IDs and an optional explicit position, but `getSource(Level)` reconstructs a position-only source whenever that position is present. It does not retain those entity IDs in the resulting client `DamageSource`. Server support for both values therefore does not establish matching native client semantics; that needs a targeted adapter if client behavior requires both. Source: `ClientboundDamageEventPacket` in the same artifact. This has not been implemented or tested in Conclave.

## Native conversion, descendants, and special boss lifecycles

Checked 2026-09-24 against the same official Minecraft 26.2 artifact and Fabric commit `0ec1d58582bd816012a8f9f1617eb4dfdeda1e93`. These source findings inform accepted Q206-Q207 and subsequent state-transfer proposals. No Conclave lifecycle integration or live compatibility test exists.

### Replacement and creation paths

`Zombie.doUnderWaterConversion` uses `Mob.convertTo`. That method creates the destination entity, copies selected native state, performs conversion finalization, adds the replacement, and discards the original for a single conversion. The entity constructor generates a fresh UUID; the inspected conversion path does not restore the old UUID. Copied native state can include tags, effects, components, and no-AI state. Single conversion also has equipment and riding transfer behavior. Copying a Conclave-looking tag therefore cannot establish that its runtime membership was transferred correctly. Source: the named methods and `ConversionType` in the [official 26.2 artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

Slime splitting occurs in inherited `AbstractCubeMob.remove`. On the server, a dying cube mob larger than size one creates two to four half-sized children using `convertTo` with `SPLIT_ON_DEATH`. Each child has a new UUID. The inspected condition checks `isDeadOrDying()` and size without requiring one particular removal reason. Inference: removing a dying owned slime during cleanup can still run its split path unless the adapter handles it. Removal alone is not evidence of completed descendant cleanup. Source: `AbstractCubeMob.remove`, `Slime`, and `ConversionType` in the same artifact.

`EvokerSummonSpellGoal.performSpellCasting` separately creates three vex with `MOB_SUMMONED`, gives them the evoker as native owner, sets a bound origin and limited life, and adds them to the server. It can also copy scoreboard-team membership. These are fresh entities while the evoker remains alive. Inference: native ownership is useful provenance, but does not itself decide Conclave scope, named-group membership, or cleanup. Source: the evoker summon goal in the same artifact.

### Fabric hook and limits

Fabric's inspected `MOB_CONVERSION` notification runs within `Mob.convertTo`, immediately before adding the new entity, while the old instance remains available. It supplies the previous instance, replacement, and conversion parameters. Its implementation does not filter out same-type splits, so the inspected slime path also reaches it. See the [event contract](https://github.com/FabricMC/fabric/blob/0ec1d58582bd816012a8f9f1617eb4dfdeda1e93/fabric-entity-events-v1/src/main/java/net/fabricmc/fabric/api/entity/event/v1/ServerLivingEntityEvents.java) and [injection location](https://github.com/FabricMC/fabric/blob/0ec1d58582bd816012a8f9f1617eb4dfdeda1e93/fabric-entity-events-v1/src/main/java/net/fabricmc/fabric/mixin/entity/event/MobMixin.java).

The callback is a notification, not cancellable admission or confirmation that insertion succeeded. It does not cover evoker summoning or establish coverage of arbitrary modded creation paths. Inference: a Conclave adapter can use it to correlate supported conversions, but must classify replacement versus splitting and verify insertion, cleanup, and recovery separately.

### Special bosses

The Ender Dragon extends `Mob`, but its `aiStep` drives an `EnderDragonPhaseManager` and flight targets. Multipart hits delegate to the dragon. Its delayed death path calls an associated `EnderDragonFight`; matching-UUID death handling can create the exit portal, gateway, and first-kill egg. `EnderDragonFight.createNewDragon` creates a fresh entity and UUID. This is not evidence that every separately spawned dragon acquires that fight association.

The Wither uses ordinary goals alongside custom movement, separate head targets, skull attacks, healing, and block destruction. `makeInvulnerable` starts a 220-tick charge and sets health to one-third maximum; completing the charge creates an explosion. Those Wither state changes keep the same entity. Sources: `EnderDragon`, `EnderDragonFight`, and `WitherBoss` in the [official 26.2 artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

Inference: inheriting `Mob` or disabling an ordinary goal selector is insufficient proof of complete AI, vulnerability, lifecycle, or cleanup support. Initial adapter coverage must state which paths it has verified, including native boss side effects, custom rendering layers, and configuration transfer. [Q206-Q207](npc-lineage.md) accept ownership and membership policy only; they do not select a universal adapter or promise support for these bosses.

## Native endings, persistence, and initial variants

Checked 2026-09-25 by static inspection of the same SHA-1-verified [official 26.2 artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar). These findings inform accepted Q216-Q218 and do not demonstrate a working Conclave adapter.

`Creeper.explodeCreeper` sets its dead state, causes the explosion, creates a lingering effect cloud where applicable, calls `triggerOnDeathMobEffects` with `KILLED`, then calls `discard`. The final `Entity.discard` removal reason is `DISCARDED`. This path bypasses `LivingEntity.die`, including its ordinary kill accounting and `dropAllDeathLoot`. Inference: neither removal reason alone nor an on-death-effect callback reliably distinguishes ordinary lethal death from committed creeper self-destruction. An adapter must not replay native death effects or invent a loot pass when classifying that outcome.

`Mob.checkDespawn` processes Peaceful removal before checking `isPersistenceRequired` and `requiresCustomPersistence`. The persistence branch skips ordinary distance and random/inactivity despawn; it does not intercept unrelated lifecycle methods. `setPersistenceRequired` sets a boolean. `Vex.tick` separately counts down limited life and then applies one point of starvation damage, resetting its countdown to twenty ticks for repeated damage. Its expiration starts a damage process, not an unconditional disappearance deadline. Inference: persistence can address ordinary distance loss while leaving native policy and lifetime behavior distinct.

| Initial-state API | Verified native behavior |
| --- | --- |
| `Zombie.setBaby` | Sets synchronized baby state and adds/removes a movement-speed modifier. Husk, drowned, and zombie villager inherit this API; they do not use the villager's `AgeableMob` growth timer. |
| `AgeableMob.setBaby` on villager | Baby starts at age -24,000. Eligible `aiStep` processing advances negative age toward adulthood. Native age-lock state exists separately; setting baby state once does not freeze it. |
| `AbstractCubeMob.setSize` | Clamps size to 1-127, refreshes dimensions, writes max-health base as size squared and movement-speed base as `0.2 + 0.1 * size`, and optionally heals. Slime additionally adjusts attack damage and experience; magma cube adjusts armor. |
| Cube dimensions and splitting | Native size multiplies default dimensions, while generic `SCALE` multiplies the resulting living-entity dimensions separately. A dying cube larger than one can create two to four integer-halved children. Slime and magma cube reject baby state. |
| Creeper charged state | `isPowered` reads synchronized state and `thunderHit` sets it. Charged explosions use twice the native strength. The inspected class has no ordinary public `setPowered(boolean)`; invoking lightning handling would have broader meaning than a boolean field assignment. |

Native attribute bounds still apply when variant methods write base stats. Inference: variant initialization must precede final authored stat overrides, health initialization, dimension checks, and reset-baseline capture. Typed validation should reject invalid values instead of relying on the native setter's clamping.

For future village-specific controls, `VillagerData` has typed `withType`, `withProfession`, and `withLevel` operations; `Villager.setVillagerData` updates synchronized state. A profession change clears existing trade offers. Native level constants span 1-5, but the record constructor only enforces a minimum of one. Type and profession use registry holders. These facts do not settle an authored trading/variant schema or its resource-pinning contract, and those controls are outside Q218's accepted initial fields.

[Q216-Q218](npc-lifetimes-and-variants.md) separate the accepted gameplay policies from these source facts. Live ordering, compatibility with other mods, native effects, and cleanup still require implementation verification.

## Fatal sources and native kill credit

Checked 2026-09-26 by static inspection of the SHA-1-verified [official 26.2 artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar) and pinned Fabric source. These facts inform accepted Q219; they do not establish implemented Conclave hooks or runtime compatibility.

`DamageSource.getEntity()` returns its stored causing entity and `getDirectEntity()` returns its stored direct entity. Neither getter looks up a recent attacker. Melee damage commonly uses the attacker in both fields. `AbstractArrow.onHitEntity` supplies the arrow as direct entity and its resolved owner as causing entity, falling back to the arrow when no owner resolves. Either field can therefore identify a non-player or nonliving entity.

`LivingEntity.die(source)` separately reads the final source and `getKillCredit()` for different native operations. `getKillCredit()` prefers stored `lastHurtByPlayer`, then stored `lastHurtByMob`. `resolvePlayerResponsibleForDamage` remembers a player attacker for 100 ticks and can also record a tamed wolf's owner. This wolf-specific credit does not replace the fatal source's causing entity and does not establish a general owner-chain policy for pets or summons.

Native fall, lava, on-fire, and drowning sources can contain neither entity field. Their victim can still have remembered native kill credit from previous combat. `DamageSource.getLocalizedDeathMessage` may consult that credit when entity fields are absent, and `CombatTracker.getDeathMessage` uses combat history for fall messages. Inference: displayed death text and remembered credit cannot establish which entity the final damage operation actually attributed.

`Creeper.explodeCreeper` supplies no fatal `DamageSource` for its own ending because it bypasses `die(source)`. Sources used for collateral explosion victims describe different operations. Neither the creeper's last attacker nor an igniting player can be recovered as a fatal source simply from this terminal path.

Fabric's pinned `ServerLivingEntityEvents.AFTER_DEATH` receives the `DamageSource` forwarded from `LivingEntity.die`. This is an observation point for that native path, not proof of committed group bookkeeping, required queue ordering, or self-discard coverage. Sources: [event contract](https://github.com/FabricMC/fabric/blob/0ec1d58582bd816012a8f9f1617eb4dfdeda1e93/fabric-entity-events-v1/src/main/java/net/fabricmc/fabric/api/entity/event/v1/ServerLivingEntityEvents.java#L152-L160) and [native injection](https://github.com/FabricMC/fabric/blob/0ec1d58582bd816012a8f9f1617eb4dfdeda1e93/fabric-entity-events-v1/src/main/java/net/fabricmc/fabric/mixin/entity/event/LivingEntityMixin.java#L70-L73).

Inference: exposing the final source preserves observable attribution, while player-owner substitution, assist credit, remembered attackers, and role/aura qualifications require separate explicit policies. Typed identity consumers must distinguish living subjects from projectiles and preserve their normal authority checks. [Q219-Q220](npc-defeat-events-and-requirements.md) accept terminal notifications and independent cause-filtered requirements over retained group records.

## Native death reward paths

Checked 2026-09-26 by static inspection of the SHA-1-verified [official 26.2 artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar). These findings support the accepted Q225 contract and do not establish implemented reward adapters or runtime compatibility.

`LivingEntity.die(source)` invokes the fatal source entity's `killedEntity` before the victim's `dropAllDeathLoot`. The latter gates its ordinary table and `dropCustomDeathLoot` with `shouldDropLoot`, then calls `dropEquipment` and `dropExperience` separately. The native gamerule is `minecraft:mob_drops`, represented by `GameRules.MOB_DROPS`. Base `shouldDropLoot` also excludes babies; `Monster` overrides the age restriction. Base `dropEquipment` is empty, so subclass paths still need verification.

`dropFromLootTable` supplies the final damage source, attacking entity, and direct attacking entity to the loot context. Recent-player attribution separately supplies `LAST_DAMAGE_PLAYER` and player luck. `LootItemKilledByPlayerCondition` checks that last-player context value. Inference: a player's earlier hit can affect native loot eligibility on an environmental death even though Q221's literal fatal-killer selection would not match that player. Public selected-table evaluation does not itself run the caller's usual loot eligibility gate.

In 26.2, creeper music discs appear in `data/minecraft/loot_table/entities/creeper.json`, conditioned on an attacker in the skeleton entity-type tag. Charged-creeper heads instead originate in `Creeper.killedEntity`, which evaluates `charged_creeper/root` on its victim before the victim's ordinary reward pass. That path has its own charged-state, loot-gate, and already-dropped-head checks. Inference: replacing a victim's normal loot table or suppressing only `dropAllDeathLoot` cannot enforce a complete no-death-items policy.

`Mob.dropCustomDeathLoot` processes equipment using `DropChances`. The native default is 0.085; `setDropChance` sets a base chance. Zero is skipped. Ordinary values still undergo recent-player eligibility, enchantment drop prevention/chance modification, a random roll, and randomized wear for damageable drops. `setItemSlotAndDropWhenKilled` marks acquired equipment through `setGuaranteedDrop`, whose chance of 2 denotes preservation. Values above 1 bypass ordinary recent-player eligibility and wear randomization. A normal 100% base chance is therefore not the native preserved-item mode. Successful equipment drops clear their slots.

`LivingEntity.dropExperience` checks consumed status and normally requires recent-player memory, `shouldDropExperience`, and the mob-drop gamerule. `isAlwaysExperienceDropper` supplies a separate special path. `getExperienceReward` applies enchantment processing over type-specific base calculations; `Mob` can add equipment bonuses. `skipDropExperience` can suppress output, while `ExperienceOrb.award` performs orb creation. Inference: choosing a fixed amount requires preserving eligibility and once-only accounting separately from amount calculation; invoking orb creation alone does not reproduce that contract.

Fabric documents table loading/replacement and runtime output hooks, including `LootTableEvents.MODIFY_DROPS`. Those hooks concern table generation and do not prove coverage of equipment, XP, or every entity-specific callback. [Fabric's 26.2 loot-table documentation](https://docs.fabricmc.net/develop/events/loot-tables).

The pinned Fabric `AFTER_DEATH` injection observes the later death-event broadcast, after ordinary reward operations. It cannot by itself prevent rewards already emitted. [Pinned native injection](https://github.com/FabricMC/fabric/blob/0ec1d58582bd816012a8f9f1617eb4dfdeda1e93/fabric-entity-events-v1/src/main/java/net/fabricmc/fabric/mixin/entity/event/LivingEntityMixin.java#L70-L73).

[Q225](npc-death-rewards-and-descendant-events.md#q225-loot-equipment-drops-and-experience) accepts separate author controls over these channels. Required implementation verification includes default suppression, selected-table replacement, attacker-side special drops on owned victims, pickup changing native slot policy, conversion, native descendants, eligibility/gamerule gates, and no duplicate payout. This source inspection does not justify deleting nearby items after death or replacing unrelated entities' global loot behavior.

## Native item blocking and damage rejections

Checked 2026-09-26 by static inspection of the verified [official Minecraft 26.2 artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar). These facts support the accepted Q228 contract. No Conclave event adapter or runtime coverage is established.

`LivingEntity.applyItemBlocking` returns an explicit blocked quantity. `BlocksAttacks.resolveBlockedDamage` clamps applicable item reductions between zero and the incoming amount. `hurtServer` subtracts the result before hurt cooldown, armor, effects, and absorption. A partial block is possible. Even a positive block can precede a cooldown rejection of the remainder; a stronger cooldown hit sends only the excess over `lastHurt` into `actuallyHurt`. The blocked quantity is consequently not a measurement of health saved.

Native invulnerability, dead/dying checks, and Fire Resistance can return before Fabric's ordinary damage veto. Native base invulnerability also handles removed state and damage-tag immunities. A false result does not identify one exhaustive reason. Zero requests differ between native player and ordinary living-entity paths; successful method return and zero health change prove neither blocking nor damage loss.

Fabric `ALLOW_DAMAGE` short-circuits on the first false callback and supplies no rejecting-mod identity. `AFTER_DAMAGE` reaches only the method's final return while the recipient is not dead/dying. It misses early immunity, veto, and cooldown returns. Its blocking flag means any positive item block, and its amounts do not represent final armor/effect/absorption resolution. `ALLOW_DEATH` runs after health subtraction and before totem handling; death veto is not equivalent to preventing the damage. Sources: [pinned event definitions](https://github.com/FabricMC/fabric/blob/0ec1d58582bd816012a8f9f1617eb4dfdeda1e93/fabric-entity-events-v1/src/main/java/net/fabricmc/fabric/api/entity/event/v1/ServerLivingEntityEvents.java), [pinned hook locations](https://github.com/FabricMC/fabric/blob/0ec1d58582bd816012a8f9f1617eb4dfdeda1e93/fabric-entity-events-v1/src/main/java/net/fabricmc/fabric/mixin/entity/event/LivingEntityMixin.java).

Conclave can instrument its own actual vulnerability-rejection branch and floor clamp. This is an implementation inference, not a native event. Q152's floor applies after absorption, before combat tracking and health subtraction, so absorption consumption can coexist with a cap. The removed health-directed input can include overkill. Reading an enabled lock after an unrelated earlier rejection cannot establish causation. Actual `DamageSource` identities and registered type remain available at the supported observation sites. A universal prevented-health amount or complete native/external rejection taxonomy does not follow from these APIs.
