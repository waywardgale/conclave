# Native item names and lore

Checked 2026-09-26 for Minecraft Java 26.2. This note records source facts and labeled integration inferences. It selects no Conclave name/lore schema, translation policy, font archive policy or rendering implementation.

## Evidence and existing contracts

The inspected official client artifact has verified SHA-1 `2dc72797acbc1b63fc16a11c4ac393605f453754`. Mojang's [26.2 metadata](https://piston-meta.mojang.com/v1/packages/987b91a95ae93b3bb78cc14d6e0bbd31bad08d59/26.2.json) identifies this [official artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar). Method evidence below comes from its named common and client classes, inspected with `javap` including private methods and bytecode. The older official release notes provide historical corroboration only; current claims were checked in 26.2.

[Q133](dialogue-formatting-and-delivery.md#q133-reusable-text-styles) accepts reusable `text_style` definitions with color, emphasis, a supported font and bounded scale. Each consuming capability must support the relevant fields. It excludes executable templates and arbitrary interaction properties. [Q136](dialogue-formatting-and-delivery.md#q136-translated-text-and-voice) defines dialogue translations and captured presentation, not native item translation semantics. [Q232-Q233](durable-item-appearances.md) retain supported real-item appearance dependencies independently of recent catalog history and preserve ordinary native component equality and item transformations. These contracts do not yet establish a native item-name/lore font or language archive implementation.

## Name precedence and anvil behavior

`ItemStack.getHoverName` first calls `getCustomName`; when that returns null it calls `getItemName`. `getCustomName` reads `DataComponents.CUSTOM_NAME`. It also has a separate written-book-title fallback, so absence of that component does not always imply absence of every custom-looking name. `getItemName` delegates to the item type's `getName(stack)`. The ordinary `Item.getName` implementation reads resolved `DataComponents.ITEM_NAME`. Source: these methods in the [26.2 artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

`ItemStack.getStyledHoverName` wraps the selected name with rarity color and adds inherited italics when `CUSTOM_NAME` is present. It does not add that italic default solely because `ITEM_NAME` is present. Explicit formatting in the name component can override inherited fields, including `italic: false` and an explicit color. This follows `Component.visit` and `Style.applyTo`, which use a component's non-null style fields before the inherited style. The distinction concerns defaults, not a prohibition on intentionally italic `ITEM_NAME` text. Sources: those methods in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar). Mojang also documents the anvil and italic distinction in its [1.20.5 release notes](https://feedback.minecraft.net/hc/en-us/articles/26136167989005-Minecraft-Java-Edition-1-20-5-Armored-Paws).

The native anvil changes `CUSTOM_NAME`. `AnvilMenu.createResult` writes a new literal component when the submitted nonblank name differs from the current displayed string. A blank name removes `CUSTOM_NAME` when present. `setItemName` likewise sets or removes that component on the result before recalculation. These rename paths do not modify `ITEM_NAME` or lore. Removing an anvil name therefore reveals the remaining underlying name, subject to the ordinary item/book behavior above. A new literal anvil rename does not preserve the former component's custom formatting or translation structure. `validateName` filters text and rejects a result longer than 50 Java string characters; this is an anvil-input limit, not an established universal serialized-name limit. Sources: `AnvilMenu.createResult`, `setItemName`, and `validateName` in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

## Lore, saving and stack identity

`DataComponents` registers both name components with persistent `ComponentSerialization.CODEC` and synchronized component codecs. `LORE` similarly uses persistent `ItemLore.CODEC` and its network codec. `ItemLore` stores a list of components and derives separate styled tooltip lines. Its codec and constructor limit the list to 256 entries. That native maximum does not establish an appropriate Conclave authoring or display budget. Sources: `DataComponents.lambda$static$6`, `$9`, `$11` and their registrations; `ItemLore` constructors and static initialization in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

Lore's default tooltip style is dark purple and italic. `ItemLore.lambda$new$0` uses `ComponentUtils.mergeStyles`, which preserves explicit fields from the line's own style and fills missing fields from the lore default. Explicit `italic: false` or color can therefore change that default. `addToTooltip` emits the derived styled lines. Lore is still subject to native tooltip display controls; its existence does not force every interface to display it. Sources: `ItemLore`, `ComponentUtils.mergeStyles`, `Style.applyTo`, `ItemStack.addToTooltip` and `getTooltipLines` in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

Native stack serialization includes the component patch. `ItemStack.copy` copies the component map, and `split` uses `copyWithCount`. Name and lore data follow those ordinary component paths. `isSameItemSameComponents` compares the item type and component-map equality, so differences in stored text components can prevent merging even when two tooltips happen to look alike. No per-copy identity is required by these text components. Sources: `ItemStack.lambda$static$1`, `copy`, `split`, `isSameItemSameComponents`, and the earlier [native item persistence research](item-appearance-persistence-research.md).

Inference: storing supported resolved formatting values inside native components can make those values independent of a later Conclave style-definition edit or catalog retirement. That does not prove the Conclave compiler copies every value correctly, and component persistence does not preserve external font or language files. Ordinary crafting, repair, conversion and other item transformations can retain, replace or discard components according to their own recipes and code; this inspection establishes no universal preservation guarantee.

## Literal, styled and translated components

`ComponentSerialization.createCodec` accepts strings, component lists and structured component objects. Structured objects combine contents, optional `extra` components and the native style codec. `PlainTextContents` stores literal `text`. `TranslatableContents` stores a `translate` key, optional `fallback` string and optional `with` arguments. These are native component representations, not a requirement to expose raw native component objects in YAML. Sources: `ComponentSerialization.createCodec` and `lambda$createCodec$0`, `PlainTextContents.lambda$static$0`, and `TranslatableContents.lambda$static$4` in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

The native `Style.Serializer` fields are color, shadow color, bold, italic, underlined, strikethrough, obfuscated, click event, hover event, insertion and font. There is no native `scale` or font-size style field. A serialized font is a resource identifier through `FontDescription.CODEC`; it is not the font's binary data. Source: `Style.Serializer.lambda$static$0` and `FontDescription` static initialization in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

Integration inference: Q133's color and supported emphasis fields have direct native counterparts. Its scale cannot be represented merely by copying a field into an ordinary native component. Any non-neutral scale would require separately verified rendering behavior or another representation. The existence of native click/hover/insertion fields does not make them accepted Conclave authoring capabilities.

## What remains when resources change

Literal text and explicit style values reside in the item component itself. Translated text retains its key, arguments and optional fallback. `TranslatableContents.decompose` resolves them against the current `Language` instance and recomputes when that instance changes. A missing translation uses the supplied fallback; without one, `Language.getOrDefault(key)` falls back to the key itself. `LanguageManager.onResourceManagerReload` loads the default language and selected language through `ClientLanguage.loadFrom`, then injects the new language. `ClientLanguage` reads `lang/<locale>.json` resources from the current resource manager. Sources: those methods in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

Fonts are also resolved from current client resources. `FontManager.prepare` reads matching font resource stacks. Its `apply` closes and clears existing font sets and installs the newly prepared ones. `getFontSetRaw` uses `missingFontSet` when the identifier is absent; that set is built with `AllMissingGlyphProvider`. An unknown font identifier therefore does not establish a readable automatic fallback to the ordinary default font. Sources: `FontManager.prepare`, `apply`, `getFontSetRaw`, its constructor and `createFallbackProvider` in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

Integration inference: retiring a resource pack does not erase the saved native name/lore component. It can change how its translation keys and font identifiers render. Copied literal text with ordinary built-in formatting needs no retired Conclave text-style definition to remain meaningful, but all displayed text still uses the receiving client's available glyphs and rendering settings. A durable custom font or translation representation would need explicit dependency retention, identity, delivery and fallback behavior. The existing model archive is not proof that such text dependencies are already captured.

## Unverified boundaries

No Conclave name/lore adapter, restart/save round trip, anvil UI test, resource-removal test, language-switch test or modified-client integration was run. No safe maximum text length, payload size, line wrapping, font profile or scale-rendering contract was derived. Specific item subclasses, recipe transformations and external mods can change name or tooltip behavior. This note does not promise immutable appearance across arbitrary player resource packs, Minecraft upgrades, unrelated mods or every native transformation.

## Further localization checks

The following checks use the same pinned 26.2 artifact and add facts for the item-localization and custom-font decisions. Fabric's [26.2 text guide](https://docs.fabricmc.net/develop/text-and-translations) documents literal components, translation keys and indexed arguments. The detailed formatting and fallback behavior below was inspected in native bytecode.

`TranslatableContents.decompose` always sends the resolved translation or fallback string through `decomposeTemplate`, including when `args` is empty. That parser recognizes `%%` as one literal percent, `%s` as the next argument and indexed forms such as `%1$s`. An absent argument, unsupported format or unmatched percent produces `TranslatableFormatException`; `decompose` catches it and uses the entire resolved template as literal text. It does not retry the component's fallback because a translation had invalid formatting. Sources: `TranslatableContents.decompose`, `decomposeTemplate`, `getArgument` and static initialization in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

Language files have another processing step. `Language.loadFromJson` replaces numeric format patterns ending in `d` or `f` with the corresponding `s` form before storing each value. Its pattern has no escape-aware exclusion for a preceding percent. Static consequence: language-file text `%%d` becomes `%%s`, which the component parser can render as literal `%s`. Simply doubling every percent is therefore not a verified lossless encoding for arbitrary authored text. The component's own fallback string does not pass through `loadFromJson`, but it still passes through `decomposeTemplate`. These observations are bytecode inferences, not a tested Conclave encoding strategy. Source: `Language.loadFromJson` and static initialization, plus the component methods above, in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

`LanguageManager.onResourceManagerReload` requests `en_us` first and then the selected language when it is different and present in the recognized language map. `ClientLanguage.loadFrom` writes those resources into one map in that order; `appendFrom` supplies map insertion to `Language.loadFromJson`. Selected-language entries replace matching default entries, while a missing selected-language entry leaves its `en_us` value available. `TranslatableContents` only uses its fallback when the key is missing from that merged map. Sources: these methods in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

Integration inference: a single generated key, authored fallback and ordinary language files do not by themselves guarantee "an exact locale miss shows the authored default" when an explicit `en_us` translation differs from that default. A client using another locale with no entry will resolve the `en_us` text before consulting the component fallback. Enforcing different semantics needs additional verified compilation or client behavior. No such adapter was implemented or selected here. Recognition of added locale metadata, pack precedence and language reloads also remain integration boundaries.

## Native font resources and dependencies

A persisted style's font uses `FontDescription.CODEC` and a native resource identifier such as `namespace:path`. `FontManager.FONT_DEFINITIONS` uses `FileToIdConverter.json("font")`, so that font ID resolves to the resource `namespace:font/path.json`, conventionally under `assets/namespace/font/path.json` in a client pack. This is a font-definition ID, not a direct operating-system font name or a bare TTF filename. Native identifier namespace/path validation applies. Sources: `FontDescription` static initialization, `Identifier.parse`, `bySeparator`, `validPathChar`, `validNamespaceChar`, `FontManager` static initialization and `FileToIdConverter` in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

The native `GlyphProviderType` registry in this artifact recognizes five provider types. This records Minecraft facilities, not Conclave's accepted import profile.

| Provider | Resource or data dependency |
| --- | --- |
| `bitmap` | A `file` identifier opened with a `textures/` prefix, plus character grid, height and ascent data. |
| `ttf` | A `file` identifier opened with a `font/` prefix, plus size, oversampling, shift and skipped-character data. The loader checks the decoded font format is TrueType. |
| `space` | An inline codepoint-to-advance map; this provider does not load a separate font file. |
| `unihex` | A `hex_file` resource opened at its specified resource path. The loader reads ZIP entries ending in `.hex`, with optional size overrides. |
| `reference` | An `id` naming another font definition, creating a font-to-font dependency. |

Sources: `GlyphProviderType` static initialization; the codecs and `load` methods of `BitmapProvider.Definition`, `TrueTypeGlyphProviderDefinition`, `UnihexProvider.Definition`; `UnihexProvider.Definition.loadData`; `SpaceProvider.Definition`; and `ProviderReferenceDefinition.unpack` in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

Font definitions contain a list of conditional providers. Their optional `filter` uses native font options, including `uniform` and `jp`. The artifact's own `assets/minecraft/font/default.json` references `minecraft:include/space`, `minecraft:include/default` and `minecraft:include/unifont`, with an option filter on the default reference. `FontManager.resolveProviders` resolves font dependencies. Sources: that resource, `FontManager.FontDefinitionFile`, `GlyphProviderDefinition.Conditional`, `FontOption`, and `FontManager.resolveProviders` in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

Integration inference: retaining one font JSON or one TTF file does not establish a complete font appearance. The supported dependency graph can include referenced fonts, textures, binary font data, compressed glyph data and provider options. The missing-font behavior recorded above still applies. Provider availability does not establish glyph coverage for every translated string, bounded parsing/rasterization cost, acceptance of every file, cyclic-reference handling suitable for Conclave, or a working ordinary-font fallback for an absent custom font. Native provider size is also distinct from a per-component text scale.

## Item synchronization and localized anvil text

Names and lore use the synchronized component codecs already described above. For a concrete native transfer path, `ClientboundContainerSetSlotPacket` reads and writes its stack through `ItemStack.OPTIONAL_STREAM_CODEC`. The component representation therefore supplies translation keys, arguments, fallback text and font references through legitimate item data. It does not transfer the referenced language files or font bytes, prove that those resources are applied, or automatically authorize an asset download. Source: that packet's buffer constructor and `write`, the component registrations above and their text codecs in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

`AnvilScreen.slotChanged` initializes its name field with `stack.getHoverName().getString()`, which is the resolved client text. `onNameChanged` submits a string through `ServerboundRenameItemPacket`. Its special conversion of an unchanged default display to an empty string applies only when `CUSTOM_NAME` is absent. `ServerGamePacketListenerImpl.handleRenameItem` passes the submitted string to `AnvilMenu.setItemName`; the native rename/removal paths described above then apply. Sources: those methods in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

Integration inference: this anvil exchange is a resolved-string workflow, not an opaque round trip of the original translatable component. A native rename can replace its translation and formatting with literal text, and removal can delete the custom-name component. Preservation behavior when the client and server resolve the current name differently requires a runtime check. This inspection does not claim that merely opening an anvil always changes a name, or that every unchanged localized name survives every native anvil operation.
