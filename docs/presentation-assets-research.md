# Presentation asset research

Checked 2026-09-17 for Minecraft Java 26.2, Fabric, and Conclave's Kotlin implementation. This note supports Q128 and the subsequently accepted Q132 GeckoLib adapter direction. It records primary-source facts separately from implementation work. The exact dependency version has not been pinned or installed, and no Conclave playback, model, or reload integration has been tested live.

## Verified model and resource capabilities

Vanilla resource packs supply textures, item/block model JSON, sound definitions and recordings, fonts, and translations. Minecraft 26.2 uses resource-pack format 88.0. Its move of beds and signs to block models illustrates that supported data-driven models are specific rendering facilities, not a universal entity-model importer. Fabric's ordinary custom-entity tutorial still defines and registers the entity, model layers, renderer, and animation behavior in code. A resource pack by itself does not add that machinery. Sources: [Minecraft 26.2 release notes](https://www.minecraft.net/en-us/article/minecraft-java-edition-26-2), [Fabric item models](https://docs.fabricmc.net/develop/items/item-models), [Fabric entity creation](https://docs.fabricmc.net/develop/entities/first-entity).

GeckoLib provides the additional installed rendering and animation machinery needed to consume authored animated entity geometry. Its current GeckoLib5 documentation specifies exported model JSON under `assets/<namespace>/geckolib/models/`, animation JSON under `assets/<namespace>/geckolib/animations/`, and PNG textures under `assets/<namespace>/textures/`. The conventional model and animation suffixes are `.geo.json` and `.animation.json`. Its Blockbench plugin exports these runtime files; a Blockbench project is not itself the documented runtime asset format. These facts do not establish support for arbitrary glTF, OBJ, other engines' animation files, or entire Bedrock add-ons. Sources: [official asset locations](https://wiki.geckolib.com/docs/geckolib5/making-models/placing-the-files/), [official export workflow](https://wiki.geckolib.com/docs/geckolib5/making-models/exporting-the-files/).

GeckoLib's `GeoModel` selects model, texture, and animation resources by identifiers, with access to render state or the animatable instance. Its 26.2 source loads and bakes model/animation JSON through Minecraft's resource manager and a resource reload listener. This supports data-driven appearance variants, but a resource pack still cannot install a new renderer, entity class, animation-controller implementation, or Kotlin behavior. Sources: [GeoModel contract](https://wiki.geckolib.com/docs/geckolib5/concepts/geomodels/basic-geomodel/), [pinned 26.2 resource-loader source](https://github.com/bernie-g/geckolib/blob/1e09655d3b54c2db959d234266fb564b90aa9382/common/src/main/java/com/geckolib/cache/GeckoLibResources.java), [pinned GeoModel source](https://github.com/bernie-g/geckolib/blob/1e09655d3b54c2db959d234266fb564b90aa9382/common/src/main/java/com/geckolib/model/GeoModel.java). The inspected branch commit contains development version 5.5.6; it is not a claim that this development version is the released dependency below.

The official support table lists Minecraft 26.2. More concretely, the maintainer's published **Fabric 26.2-5.5.5** release is available as `geckolib-fabric-26.2-5.5.5.jar`, published on 2026-09-06. Its actual `fabric.mod.json`, inspected in memory, declares GeckoLib 5.5.5, MIT, Fabric Loader `>=0.19`, Fabric API `>=0.152.1+26.2`, Java `>=25`, and Minecraft `>=26.2`. This establishes a released Fabric build for the requested game version, rather than inferring compatibility from another loader or Minecraft version. Sources: [official support table](https://wiki.geckolib.com/docs/geckolib5/), [release page](https://modrinth.com/mod/geckolib/version/7gaQHok7), [release metadata](https://api.modrinth.com/v2/version/7gaQHok7), [published artifact](https://cdn.modrinth.com/data/8BmcQJ2H/versions/7gaQHok7/geckolib-fabric-26.2-5.5.5.jar).

The source license is MIT. It permits use, modification, and redistribution subject to retaining its copyright and permission notice. The published artifact also contains `LICENSE.txt`. This is a permissive dependency candidate; its license does not grant rights to unrelated imported artwork or voice recordings. Source: [pinned GeckoLib MIT license](https://github.com/bernie-g/geckolib/blob/1e09655d3b54c2db959d234266fb564b90aa9382/LICENSE).

## Verified sound, dialogue, and localization facilities

Minecraft sound assets use OGG Vorbis recordings and entries in `assets/<namespace>/sounds.json`. Fabric recommends mono audio for positional playback. The definition's `subtitle` names a translation key in the resource pack's language files; vanilla shows that subtitle when the player has subtitles enabled. A boss taunt or spoken line can therefore be an authored recording with a localized caption. This does not provide text-to-speech, automatically translated recordings, lip synchronization, or a dialogue scheduler. Sources: [Fabric custom sound assets and subtitles](https://docs.fabricmc.net/develop/sounds/custom), [Fabric text and translations](https://docs.fabricmc.net/develop/text-and-translations).

**A new recording does not inherently require a new sound registry entry.** Inspection of Mojang's official 26.2 client binary confirmed that `PlaySoundCommand.playSound` takes a sound `Identifier`, constructs `SoundEvent.createVariableRangeEvent(identifier)`, wraps it in `Holder.direct`, and sends `ClientboundSoundPacket` to selected players. The packet carries the sound holder, category, coordinates, volume, pitch, and seed. Thus an installed generic playback path can play newly published, successfully loaded resource-pack sound IDs without registering or compiling each dialogue line. Fabric's tutorial demonstrates registration for fixed mod sounds; that tutorial is not a requirement to register every data-authored cue. Primary artifact: [official Minecraft 26.2 client](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar), identified by [official version metadata](https://piston-meta.mojang.com/v1/packages/987b91a95ae93b3bb78cc14d6e0bbd31bad08d59/26.2.json).

The same binary exposes identifier-based `SimpleSoundInstance` construction, non-attenuated UI/local sound instances, and `EntityBoundSoundInstance` for a moving sound source. Vanilla's selected-player packet path establishes targeted delivery; positional playback and recipient selection are separate controls. Fabric also documents server-originated entity and location sounds, categories, volume/pitch, and custom dynamic sound instances. Conclave must define which recipients receive a cue, whether it follows an entity or plays locally, and how an individual playback is stopped; those semantics are not supplied by an OGG file. Sources: [Fabric sound playback](https://docs.fabricmc.net/develop/sounds/using-sounds), [Fabric dynamic sounds](https://docs.fabricmc.net/develop/sounds/dynamic-sounds), [official client binary](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

## Proposed Conclave integration, not an existing implementation

Recommend one installed GeckoLib5 presentation adapter for custom animated Conclave NPC appearances. A Conclave-owned NPC can select captured model, animation, and texture identifiers through that adapter; new authored appearances need not create a native entity registration each time. Conclave remains responsible for gameplay, collision, AI, authoritative event timing, and presentation-event delivery. Pack geometry and animation clips supply appearance and motion within the adapter's supported features. This is the smallest evidenced approach that covers custom animated NPCs without implementing a second geometry and animation engine.

Keep the runtime format explicit: supported GeckoLib-exported model/animation JSON plus textures, supported vanilla model assets where appropriate, and OGG Vorbis/sound definitions for ability audio and recorded speech. The importer needs format/dependency validation and clear unsupported-feature errors. A new renderer feature or behavior still requires installed code. GeckoLib is a mod dependency, not a library downloaded or executed from an authored resource pack.

Preserve the accepted Q75/Q124 workflow: in-game import and publication, bounded transfer over the authenticated Minecraft connection, local staging, consent, and readiness acknowledgement. Do not introduce HTTP pack URLs, another port, external upload steps, or a CLI. Activate resources outside the receiving player's active attempt. Version the complete referenced asset graph, including model/animation/texture references, sound-event IDs, recording paths, and translation keys where old consumers must retain their text. A pack UUID does not version those identifiers automatically.

Before selecting the exact dependency, test the released Fabric build with two concurrently retained appearance/animation/audio revisions, then reload and retire an unreferenced revision. Verify that the adapter resolves each consumer's captured identifiers after cache rebuilding and that existing persistent consumers keep their presentation. The source reload path establishes feasibility; it does not prove Conclave's version retention or reload recovery. No arbitrary format support or built-in TTS is implied.

## NPC renderer and attachment follow-up

Checked 2026-09-20 for the next NPC presentation decisions. GeckoLib documents replacement renderers for existing vanilla or modded entities without a new `EntityType`. The installed integration supplies an animation wrapper, model, and renderer; publishing assets alone does not install that code. This supports retaining the original NPC's server gameplay while changing its client appearance. See [replacement introduction](https://wiki.geckolib.com/docs/geckolib5/entities/replaced-entities/intro/) and [replacement renderer requirements](https://wiki.geckolib.com/docs/geckolib5/entities/replaced-entities/creating-the-renderer/).

The inspected [replacement renderer](https://github.com/bernie-g/geckolib/blob/1e09655d3b54c2db959d234266fb564b90aa9382/common/src/main/java/com/geckolib/renderer/GeoReplacedEntityRenderer.java) accepts additional Geo render layers, calls the base entity presentation path, and extracts common living render state, including movement, invisibility, and hurt/death overlays. It does not call the original type-specific renderer. The [layer container](https://github.com/bernie-g/geckolib/blob/1e09655d3b54c2db959d234266fb564b90aa9382/common/src/main/java/com/geckolib/renderer/layer/GeoRenderLayersContainer.java) starts with its own empty collection. Original armor, hands, eyes, saddles, and other special layers therefore do not transfer automatically. Name visibility has an existing implementation path, but positioning for custom proportions and preservation of special visuals need verification.

The general [block and item layer](https://github.com/bernie-g/geckolib/blob/1e09655d3b54c2db959d234266fb564b90aa9382/common/src/main/java/com/geckolib/renderer/layer/builtin/BlockAndItemGeoLayer.java) supports rendering native item models at named bones with data extracted from the related entity. A focused Conclave layer that passes the original NPC's current equipment is an implementation inference from this extension point. The ready-made [item-in-hand layer](https://github.com/bernie-g/geckolib/blob/1e09655d3b54c2db959d234266fb564b90aa9382/common/src/main/java/com/geckolib/renderer/layer/builtin/ItemInHandGeoLayer.java) requires a living-entity animatable, whereas the replacement renderer uses a separate non-entity animation wrapper, so that convenience layer cannot simply be installed unchanged.

The [armor layer](https://github.com/bernie-g/geckolib/blob/1e09655d3b54c2db959d234266fb564b90aa9382/common/src/main/java/com/geckolib/renderer/layer/builtin/ItemArmorGeoLayer.java) likewise needs explicit bone mappings and a compatible living animatable. Its humanoid body segment means chest and must not be confused with Minecraft's separate animal `body` equipment slot. Arbitrary armor fit, animal armor, saddle rendering, and special layers are not established by the general replacement API.

Native item models use their own client definitions, textures, and hand, ground, GUI, or other display transforms. They can provide the appearance of a held attachment or carried/dropped relic without becoming an NPC animation skeleton. See Fabric's [item-model documentation](https://docs.fabricmc.net/develop/items/item-models) and [item appearance documentation](https://docs.fabricmc.net/develop/items/item-appearance).

Conditional routing to a retained native renderer for an unrelated NPC or a viewer lacking the captured custom assets would be Conclave's responsibility. These sources do not provide an automatic per-viewer fallback implementation. Q162-Q163 in [NPC equipment visuals and model fallback](npc-model-presentation.md) are accepted policy, distinct from these library facts and still requiring Conclave integration verification.

This NPC follow-up inspected the same pinned 26.2 development revision identified above as 5.5.6. The separately checked published artifact remains Fabric 26.2-5.5.5. No compilation, live test, exact released-artifact comparison, or blanket entity/mod compatibility proof was performed. Exact dependency selection and the adapter still require implementation verification.

## Managed relic presentation and interaction facilities

Checked 2026-09-22. Inspection of the [official 26.2 client artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar) confirmed `Display.ItemDisplay`, its `setItemStack` and `setItemTransform` methods, and its native renderer. The artifact also contains `Interaction` with width, height, and response setters. Its `isPickable()` returns true, `canBeHitByProjectile()` returns false, and its tick method is empty. These are native facilities, not evidence that Conclave has implemented a managed relic.

Mojang's [display and interaction entity documentation](https://www.minecraft.net/en-us/article/minecraft-java-edition-1-19-4) describes separate purposes for their dimensions. Display width and height describe rendering culling bounds; interaction width and height describe the interaction target's bounding box. The article dates from their introduction and is supplemented here by the 26.2 artifact inspection. Visual scale or culling bounds must not be mistaken for pickup geometry. Native pickability also does not establish the proposed distinction between Conclave Use targeting and ordinary attacks aimed through a relic.

Fabric's [26.2 item-model documentation](https://docs.fabricmc.net/develop/items/item-models) documents item appearance and display transforms, including `ground`, `fixed`, and `gui`. Its [HUD documentation](https://docs.fabricmc.net/develop/rendering/hud) exposes `HudElementRegistry` for client HUD elements. Rendering a native item visual and displaying carried state are therefore plausible integration choices without using inventory as the ownership record. That conclusion is an implementation inference from the rendering facilities.

A managed relic with separate presentation, interaction, and holder HUD state still needs its Conclave adapter. A display plus interaction entity is one candidate, not a selected architecture or a guarantee of the entire input contract. Verify block occlusion, reach, fresh/both-hand input, placement clearance, nonblocking behavior, attack handling, per-viewer fallback, and synchronized visual/target cleanup. Existing [interaction research](interaction-input-research.md) records the other input gaps.

The accepted GeckoLib adapter initially targeted NPC appearances, and Q188 now accepts adding a managed world-relic consumer. That consumer still requires its own verified integration and supported model-state profile. Native item rendering, an authored native fallback, and a carried player-body attachment are distinct consumer contracts; none follows automatically from the presence of a geometry resource or NPC renderer.

## Player render layers for carried objects

Checked 2026-09-22. Fabric's pinned 26.2 [render-layer registration callback](https://github.com/FabricMC/fabric/blob/0ec1d58582bd816012a8f9f1617eb4dfdeda1e93/fabric-rendering-v1/src/client/java/net/fabricmc/fabric/api/client/rendering/v1/LivingEntityRenderLayerRegistrationCallback.java) explicitly supports adding a layer to `AvatarRenderer`. Its [player-renderer hook](https://github.com/FabricMC/fabric/blob/0ec1d58582bd816012a8f9f1617eb4dfdeda1e93/fabric-rendering-v1/src/client/java/net/fabricmc/fabric/mixin/client/rendering/EntityRenderersMixin.java) invokes the callback for player renderers, including the slim variant. This is an evidenced extension point for an added carried-object layer without replacing the entire player renderer.

Inspection of the [official 26.2 artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar) confirmed that `LivingEntityRenderer.submit` prepares the model's animated pose before submitting layers. `HumanoidModel` exposes body and head parts. `CustomHeadLayer` demonstrates applying model/head transforms and submitting an item visual. Using these facilities for a carried relic is an implementation inference; Conclave still needs its own state extraction and item or model submission.

Visibility is not automatic for a new layer. Native render state exposes both `isInvisible` and viewer-relative `isInvisibleToPlayer`, and layers such as `CapeLayer` check visibility themselves. The inspected `AvatarRenderer.renderHand` submits the hand separately without traversing body layers. These facts support separating carried body rendering from first-person item use, but the Conclave layer must still handle its own visibility, occlusion, camera-subject, and spectator policy.

Verify attachment positions across standing, crouching, swimming, flying, riding, and scaled-player poses, as well as ordinary player variants. Player-model replacements and first-person-body mods need explicit compatibility testing. The native extension point does not guarantee those combinations or provide revision-aware fallback and cleanup.

The verified layer facilities do not establish animation continuity across hidden, culled, carried/unheld, or replaced visual objects. Q190 accepts retaining logical playback identity and elapsed simulation time as a Conclave policy requiring its own adapter and synchronization. GeckoLib's presence alone does not prove that behavior. No carried-object implementation or live integration test was produced by this research.

## Private world-space pattern clues

Checked 2026-09-24. The cached [official Minecraft 26.2 client artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar) was verified against SHA-1 `2dc72797acbc1b63fc16a11c4ac393605f453754`. Its `OrderedSubmitNodeCollector` exposes `submitText`, `submitItem`, and `submitCustomGeometry`. Custom geometry receives a vertex consumer with texture coordinates, and `RenderTypes.entityCutout` accepts a texture identifier. Inference: an installed Conclave adapter can compose token labels, native item visuals, and textured planes as world presentation without creating gameplay objects. The binary does not provide Conclave's symbol layout or asset-version handling.

`DisplayRenderer.calculateOrientation` uses entity yaw and pitch for fixed orientation and separate camera-dependent branches for billboard modes. `TextDisplayRenderer` distinguishes see-through text from ordinary depth-aware text. Fabric's [26.2 world-rendering guide](https://docs.fabricmc.net/develop/rendering/world) also distinguishes an ordinary occluded pipeline from a through-wall variant that disables depth state. Conclave must deliberately choose ordinary depth testing for every clue component, including labels. A waypoint example with disabled depth is not the intended clue-rendering policy.

Fabric's [networking guide](https://docs.fabricmc.net/develop/networking) documents sending a custom payload to an individual server player through `ServerPlayNetworking.send` and receiving it through `ClientPlayNetworking.registerGlobalReceiver`, including a client-local visual example. The world-rendering guide exposes separate extraction and drawing stages through `LevelExtractionEvents` and `LevelRenderEvents`. Inference: targeted presentation payloads and client-local render state are an evidenced route to private world clues; their lifetime and permissions remain Conclave's work.

Ordinary server display entities do not enforce an authored private audience by themselves. In the inspected artifact, `ChunkMap.TrackedEntity.updatePlayer` considers range, chunk tracking, and `broadcastToPlayer`; the base entity implementation allows broadcast. `ServerEntity.sendPairingData` and `sendDirtyEntityData` distribute synchronized metadata to tracking clients, while displays carry their text/item presentation in synchronized entity data. Inference: broadcasting a normal display and hiding it locally for nonrecipients would disclose its contents. A private cue needs server-controlled delivery or additional tracking rules before data reaches a client.

The accepted [world clue contract](world-pattern-clues.md) uses a Conclave presentation adapter and keeps its audience separate from normal NPC/relic visibility. Named-location transforms, panel dimensions, item/texture/text composition, occlusion around translucent terrain, resource revisions, recipient changes, reconnects, dimensions, and cleanup require implementation and runtime verification. This research selects no additional dependency and does not claim a tested renderer or anti-cheat boundary against an authorized recipient inspecting data already sent to their client.

## Model lighting, visual bounds, and native item models

Checked 2026-09-26 against the same SHA-1-verified [official Minecraft 26.2 artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar) and GeckoLib commit `1e09655d3b54c2db959d234266fb564b90aa9382`. This is the previously inspected 5.5.6 development source, not a new verification of released 5.5.5. These findings support the accepted Q229-Q231 contracts. No Conclave rendering integration or live verification exists.

### Lighting

GeckoLib's entity render state reads an optional `PACKED_LIGHT` value, and its object renderer accepts packed light. A Conclave normal/fullbright choice therefore has a direct adapter path for entity and managed-object geometry. Its `AutoGlowingGeoLayer` draws an emissive overlay, normally deriving a glow-mask filename; overriding its texture-resource method permits an explicit texture ID. The overlay uses the same geometry and UV layout. Sources: [entity light handling](https://github.com/bernie-g/geckolib/blob/1e09655d3b54c2db959d234266fb564b90aa9382/common/src/main/java/com/geckolib/mixin/client/EntityRenderStateMixin.java), [object renderer](https://github.com/bernie-g/geckolib/blob/1e09655d3b54c2db959d234266fb564b90aa9382/common/src/main/java/com/geckolib/renderer/GeoObjectRenderer.java), [emissive layer](https://github.com/bernie-g/geckolib/blob/1e09655d3b54c2db959d234266fb564b90aa9382/common/src/main/java/com/geckolib/renderer/layer/builtin/AutoGlowingGeoLayer.java).

These facilities change surface rendering, not world-light propagation, bloom, or through-wall outlining. Full packed light does not prove all directional shading disappears. Separate equipment layers submit their own rendering. Platform-specific emissive paths and visibility handling need consumer verification; a non-entity object does not inherit an entity's visibility rules merely by using the same model.

### Culling

GeckoLib parses `visible_bounds_width`, `visible_bounds_height`, and `visible_bounds_offset` into metadata but explicitly does not use them for rendering bounds. Its replacement renderer does not replace native culling. Source: [geometry description](https://github.com/bernie-g/geckolib/blob/1e09655d3b54c2db959d234266fb564b90aa9382/common/src/main/java/com/geckolib/loading/definition/geometry/GeometryDescription.java), [replacement renderer](https://github.com/bernie-g/geckolib/blob/1e09655d3b54c2db959d234266fb564b90aa9382/common/src/main/java/com/geckolib/renderer/GeoReplacedEntityRenderer.java).

In the inspected 26.2 artifact, `EntityRenderer.shouldRender` applies distance eligibility and then a frustum check using overridable `getBoundingBoxForCulling`, whose default is the entity's physical box. Native displays separately derive a box from their culling width/height; zero in either dimension disables their frustum check. Mojang's [display documentation](https://www.minecraft.net/en-us/article/minecraft-java-edition-1-19-4) describes those display controls. These are not Conclave interaction dimensions or a model animation envelope.

A finite authored visual box can feed a Conclave renderer adapter. It must transform that box with the consumer's position, rotations, physical and visual scales, and carried attachment. This is an implementation inference. The inspected facilities establish no automatic guaranteed envelope over all animation clips and equipped items. Larger bounds alone do not extend entity tracking, render distance, or server simulation.

### Per-stack item models

Minecraft 26.2 `DataComponents.ITEM_MODEL` holds a persistent, synchronized identifier. `ItemModelResolver.appendItemLayers` reads it from the actual stack; both living and nonliving item rendering reach that resolver. `ClientItemInfoLoader` loads client item definitions from `assets/<namespace>/items/<path>.json`. Mojang's [item-model specification](https://www.minecraft.net/en-us/article/minecraft-java-edition-1-21-4) explains this resource distinction. The reference is not a raw PNG, GeckoLib geometry, or a direct `models/item` path.

Real equipment can carry the component. GeckoLib's [block and item attachment layer](https://github.com/bernie-g/geckolib/blob/1e09655d3b54c2db959d234266fb564b90aa9382/common/src/main/java/com/geckolib/renderer/layer/builtin/BlockAndItemGeoLayer.java) can render resolved native item state. Using a rendering-only stack for a managed relic or icon is a Conclave integration inference; it does not require granting the relic inventory ownership.

Missing client item definitions produce native missing-model behavior, not an automatic base-item fallback. Conclave must implement its accepted fallback explicitly. Native worn armor uses a separate equipment asset and renderer, so an item-model choice does not replace worn armor geometry. Contextual item definitions can choose different visuals by display context and stack/entity state. A real dropped item retains its item-model component; persistent asset references therefore outlive the NPC and can outlive the attempt. Retention, restart, and unavailable-viewer handling must be settled before such a consumer can ship.

A follow-up checked the imported-bounds ambiguity: GeckoLib's [stored properties](https://github.com/bernie-g/geckolib/blob/1e09655d3b54c2db959d234266fb564b90aa9382/common/src/main/java/com/geckolib/cache/model/ModelProperties.java) describe world units, while Microsoft's [geometry schema](https://learn.microsoft.com/en-us/minecraft/creator/reference/content/schemasreference/schemas/minecraftschema_geometry_1.21.0?view=minecraft-bedrock-stable) describes model-space units and an offset relative to the entity. The inspected documentation does not establish a common center/base and conversion convention suitable for automatic Conclave defaults. Computing supported rest-pose geometry bounds and documenting Conclave's own explicit dimensions is a design choice requiring implementation.

In the verified native artifact, removing `ITEM_MODEL` from a stack can create an explicit absent-component override; the item resolver then returns without drawing it. That is not a base-item fallback. A rendering-only copy can instead restore this component from the registered item's prototype through `ItemStack.copyFrom`, preserving its other components. A fresh default instance is appropriate only when a pristine default visual is intended. The prototype can itself be modded or lack a usable model, so restoring it cannot guarantee a vanilla appearance.
