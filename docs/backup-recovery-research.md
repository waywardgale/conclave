# Native backup and recovery boundaries

Checked 2026-09-29 through static inspection of the SHA-1-verified [official Minecraft Java 26.2 client artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar), digest `2dc72797acbc1b63fc16a11c4ac393605f453754`, and the Fabric 26.2 lifecycle sources linked below. The artifact contains the inspected common server classes. No Conclave persistence adapter, maintenance coordinator, backup operation, or restore test exists. These are facts and integration limits, not an accepted backup policy.

## Existing Conclave constraints

- [Q120](cleanup-and-restart.md#q120-interrupted-attempts-after-a-server-restart) ends interrupted attempts and retains idempotent cleanup, player recovery, outside-attempt graves, and start-rule rearm state. It does not resume attempts or replay rewards and death consequences.
- [Q254-Q255](durable-completion-and-reward-storage.md) require durable success/allocation commitment, preservation of pending and uncertain obligations, and conservative replay-prevention records. Native inventory, XP and player saves remain a separate persistence boundary. Restoring unrelated stores from different times is explicitly unresolved.
- [Q253](reward-generation-and-review.md) permits operator review only for an existing uncertain transfer. It cannot recreate missing success or allocations, reroll contents, use matching items as delivery proof, or roll inventories backward to reconcile accounting.
- [Q232-Q233](durable-item-appearances.md) require retained item resources to accompany the complete world backup. Resource identity is neither item ownership nor a reward receipt. [Q260-Q261](durable-item-localization-and-fonts.md) extend retention to translations and font dependencies.
- [Q272-Q273](content-upgrades-and-startup-recovery.md) distinguish editable content upgrades from durable-storage migration. Unknown global ownership can prevent safe startup; a consistent verified backup may be necessary. These contracts do not supply a storage migration, backup protocol, or force-start escape hatch.

## Saving is separate from a consistent snapshot

`SaveAllCommand.saveAll` calls `MinecraftServer.saveEverything(true, flush, true)`. `saveEverything` calls `PlayerList.saveAll` first and then `saveAllChunks`. The latter saves each level, level metadata and server saved data. With flushing enabled, `ServerLevel.save` waits for saved data, requests chunk saving, and uses the entity manager's `saveAll`; `ChunkMap.saveAllChunks(true)` flushes points of interest, processes unloads, and joins the region-storage synchronization future. These paths provide native save/flush work, but contain no shared transaction with an independent Conclave store. Source: the named methods in the [official artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

`PlayerDataStorage.save` writes a temporary compressed player file and invokes `Util.safeReplaceFile` for the player file and its old version. It catches `Exception`, logs a warning, and returns. `MinecraftServer.saveAllChunks` returns whether it iterated a level, not an aggregate result proving every player file saved successfully. Therefore a normal overall save return or command success message alone is insufficient evidence that every required write succeeded. This is an inference from those control flows, not a tested failure-injection result. Source: `PlayerDataStorage.save`, `MinecraftServer.saveAllChunks` and `SaveAllCommand.saveAll` in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

`LevelStorageAccess.makeWorldBackup` checks that its existing world lock is valid, creates a ZIP, and walks the world directory. Its visitor copies each encountered file, excluding `session.lock`. It does not first save the running server, stop writers, or create a filesystem snapshot. It only traverses that world directory; arbitrary sibling configuration, executable mods and external databases are not included by this method. Source: `LevelStorageSource.LevelStorageAccess.makeWorldBackup` and its anonymous file visitor in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

The resulting limitation is specific: a save followed by a background directory copy is not established as a consistent backup. Files can be observed at different write states unless the implementation separately controls the writers or uses a verified coordinated snapshot facility.

## Tick freeze and save-off do not stop all writes

`TickRateManager.isEntityFrozen` exempts players and entities carrying players. `MinecraftServer.tickChildren` continues its connection and player-list ticking paths when ordinary game elements are frozen. `tickServer` also continues its autosave scheduling. A game-tick freeze is therefore not a general maintenance write barrier. Source: `TickRateManager.isEntityFrozen`, `MinecraftServer.tickChildren` and `tickServer` in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

`SaveOffCommand` calls `MinecraftServer.setAutoSave(false)`, which changes each level's `noSave` flag. `PlayerList.remove` still invokes the player save path directly; that path saves player NBT, statistics and advancements. The flag does not gate these calls or control another mod's database. Consequently save-off cannot be treated as a server-wide prohibition on persistence. Source: `SaveOffCommand`, `MinecraftServer.setAutoSave`, `PlayerList.remove` and `PlayerList.save` in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

## Shutdown, locks, and Fabric events

`MinecraftServer.stopServer` closes packet processing and the listener, saves and removes players, drains chunk shutdown work, performs a flushing world save, closes levels and saved-data resources, and closes its `LevelStorageAccess`. `ServerChunkCache.close` saves then closes its storage and chunk resources; `ServerLevel.close` also closes its entity manager. Some close exceptions are logged while shutdown continues. The existence of this path does not prove that every write succeeded or that every installed mod's background worker has stopped. Source: these methods in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

`DirectoryLock.create` holds a Java file lock on `session.lock`; `LevelStorageAccess.close` releases it through `DirectoryLock.close`. This coordinates access with software that honors that lock. Holding it does not prevent the same running server from changing its own files and is not a snapshot transaction. Source: `DirectoryLock` and `LevelStorageAccess.close` in the [artifact](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

Fabric documents `SERVER_STOPPING` before listener closure/player disconnection, with levels still mutable, and `SERVER_STOPPED` after levels and players have unloaded. Its mixin places these at the head and tail of `stopServer`. Thus the stopped callback follows native world-lock release on the inspected normal path. A backup or replacement at that point needs its own verified exclusive-access coordination. Sources: [lifecycle event contract](https://github.com/FabricMC/fabric-api/blob/26.2/fabric-lifecycle-events-v1/src/main/java/net/fabricmc/fabric/api/event/lifecycle/v1/ServerLifecycleEvents.java), [lifecycle mixin](https://github.com/FabricMC/fabric-api/blob/26.2/fabric-lifecycle-events-v1/src/main/java/net/fabricmc/fabric/mixin/event/lifecycle/MinecraftServerMixin.java).

The same mixin places `BEFORE_SAVE` and `AFTER_SAVE` around `saveAllChunks`, rather than around `saveEverything` or a cross-store commit. These notifications do not add backup isolation or report an aggregate player/store success result. Source: [Fabric lifecycle mixin](https://github.com/FabricMC/fabric-api/blob/26.2/fabric-lifecycle-events-v1/src/main/java/net/fabricmc/fabric/mixin/event/lifecycle/MinecraftServerMixin.java).

## What remains unverified

The inspected APIs do not establish a simple safe live backup while ordinary players, commands and independent storage writers continue operating. A closed world with completed writes and exclusive access is an identifiable native boundary; turning it into an in-game operation still requires a coordinator. Closing world storage is distinct from requiring the JVM process to have exited. The choice of supported maintenance/backup flow remains a product decision.

Verification must establish the exact Conclave store and archive flush/close semantics; drain or exclusion of admitted operations; native write-error detection; complete included data; lock ownership during copying and replacement; interrupted backup/restore handling; integrity checking; storage-format compatibility; and reconciliation before world admission. A database backup facility cannot alone include Minecraft's world and player files. No generic facility for restarting a closed dedicated world, replacing executable mods, or serving an in-game screen when required server code cannot initialize was established by this inspection.

Storage migration must be designed against the selected storage implementation. No evidence here proves atomic migration, downgrade support, compatibility with arbitrary mod stores, or recovery after independently restored files. Unsupported combinations require explicit diagnostics rather than inferred empty state. The research adds no companion CLI requirement and does not change the accepted in-game authoring and administration goal.
