# Mechanic startup and parameter contracts

Status: Q167-Q168 are accepted. The user accepted `type: layers`, `export.events`, typed reusable-mechanic parameters, independent activations, and existing event ordering. The development compiler and runtime implement startup ordering and a subset of the accepted parameter kinds. See [implementation status](implementation-status.md) for current evidence and remaining work.

## Q167: a started event before child mechanics begin

Accepted: provide a standard `started` event for each new encounter attempt, phase activation, and mechanic activation. In a scope that supports rules, allow `on.source: self` to refer to that rule's containing encounter, phase, or layers activation. Keep the familiar `on` / `if` / `do` form instead of adding a second startup-action syntax.

```yaml
rules:
  - id: create_guard
    on:
      source: self
      event: started
    do:
      - spawn:
          npc: shielded_guard
          location: entrance
          group: guard
```

This fragment belongs to an encounter, phase, or layers body with the referenced NPC and location available. It creates its group once when that enclosing activation starts. A later child mechanic can use the group's declared producer under Q93. The example describes framework syntax, not a bundled encounter.

`self` always means the scope containing the rule. It does not change to the source of the last event, a selected player, or the NPC targeted by an action. It is a special event-source form, not a new `scope` value or a general entity-target alias. Ordinary named sources, including `{mechanic: child_id}`, keep their existing meanings. A containing rule can also observe a child's public `started` event through that named source.

### Initialization order

For an encounter, admit `started` only after the accepted admission and readiness checks succeed and its revision, roster, and arena ownership are established. Bind the activation's configuration and initialize declared private state and subscriptions before admitting its `started` event. Local counter initial values and declared timer state are available to the handlers. Automatic timers and configured duration/deadline timing keep their accepted activation-based simulation clock; handling startup does not grant a hidden extra timer window.

Queue `started` through Q68. Run its matching rules in the ordinary declared order, with each rule's actions in order, before activating that scope's child mechanics. An encounter starts its initial phase after its own startup handling; a phase starts its objective and background mechanics after its handling; a layers mechanic starts its children after its handling. Preserve Q165's objectives-before-background order and declaration order within each section. This introduces a defined setup point without changing the one-active-phase model.

Events generated by startup actions join the existing queue and are not delivered recursively. Scheduling the next activation stage must preserve admitted event order. A pending documented retry or delayed required startup operation keeps dependent child activation pending without blocking the server thread. The existing lifetime, timing, cancellation, and work limits still apply; startup cannot wait indefinitely or pause simulation for the entire server.

If required startup work fails, use Q69's technical-error or explicitly handled recoverable outcome. Do not start children after their owning activation has been stopped, cancelled, or replaced. A condition that merely fails its startup rule's guard skips that rule normally; it does not keep waiting for the guard to become true.

### One event per real activation

Emit `started` once per new activation. Re-entering a phase, starting a new sequence step, or starting a new repeat iteration creates its own relevant activation and may emit again. A reconnect, HUD refresh, asset reload, configuration publication, or restored persistent aura does not restart an encounter or mechanic and emits no such event.

Use the normal immutable provenance and activation identity. Do not fabricate a triggering player when automatic startup has none. Existing `once`, cooldown, and `per_player` validation retain their meanings; `per_player` is unavailable when this event provides no unambiguous triggering player. Terminal notifications keep their existing delivery and cancellation rules, and this decision never reactivates ended subscriptions for cleanup callbacks.

## Q168: readable typed parameters and constraints

Accepted: complete the `parameters` declaration with a small registered type catalog, optional `name` and `description`, typed `default`, and applicable constraints. The parameter map key is its stable ID. Keep Q79's rule that a parameter without a default is required. Defaults are schema-valid literal values or typed configuration, not expressions or references to another parameter or an event.

```yaml
parameters:
  area:
    type: area
  players_required:
    type: integer
    default: 3
    min: 1
    max: 6
  duration:
    type: duration
    default: 10s
    min: 1s
    max: 1m
```

These are author-chosen bounds for this illustrative definition, not framework-wide party or duration limits. Bind values through the existing `{parameter: name}` form. The editor uses the type and constraints for appropriate controls and completion, while the server applies the same validation to YAML entered by humans or agents.

| Parameter family | Initial contract |
| --- | --- |
| Scalars | `boolean`, `integer`, finite `number`, `duration`, explicit `percentage`, and literal `string`. Preserve documented units and reject implicit duration/percentage coercion. |
| Choices | `enum` with a nonempty, unique `values` list of literal strings. A default must be one of those values. |
| Spatial references | `area` and `location`, retaining the caller's typed arena binding. A location cannot satisfy an area parameter. |
| Content references | Registered typed definition, asset, and native registry references where a supported consuming field exists. Include `npc`, `aura`, `relic`, `model`, `dialogue`, and `text_style` definition references; retain the existing item, effect, damage-type, and asset contracts rather than treating them as interchangeable strings. |
| Runtime selection and references | `players` for an immutable player-selection configuration, `group` for a declared spawn-group reference, and `role` for a declared assignment under Q169. References retain the caller's permitted scope and activation. These remain distinct from an NPC definition. |

Each advertised type must have a registered validator, editor schema, and compatible receiving field. A parameter type does not create a missing gameplay capability. Do not introduce an untyped `any`, arbitrary YAML map, arbitrary action or rule list, script, or expression parameter. Additional parameter kinds need a registered contract rather than a filename or Kotlin class name in the manifest.

### Bounds and substitution

Use inclusive `min` and `max` for numeric, duration, and percentage types, with values in the parameter's units. Use `max_length` for strings. Reject constraints that do not apply to that type, contradictory bounds, non-finite numbers, invalid enum values, and defaults outside their declared constraints. Caller values must satisfy both the parameter declaration and every consuming capability's own field constraints after binding. A broad parameter cannot bypass a capture minimum, entity adapter limit, or native registry validation.

Preserve ordinary literal text in strings. A string that resembles `{event: player}` or an arithmetic expression remains text in a string field; it does not become executable configuration. Parameter references occupy a whole typed value, never part of a string. Reject missing required arguments, unknown `with` keys, incompatible reference kinds, and recursive definition expansion before starting the affected attempt.

Resolve caller-supplied references in the caller's namespace and scope before binding them, including references nested in a supported selection value. Internal literals in the reusable definition still resolve in that definition's namespace. Report the caller argument and the consuming definition field when a binding fails, so an author can identify which file to fix. Uninstantiated reusable definitions may be stored with required parameters; actual uses and declared encounter/arena pairings must validate with concrete bindings.

### Fixed configuration, current selection

Binding a `players` parameter fixes the selection configuration, not a historical list of players. Each consuming action or live occupancy check evaluates it according to its existing contract. For example, a filter for players carrying an aura sees who carries it when the action executes. Each individual action still snapshots its recipients once. Selecting players once and retaining an assignment uses the existing explicit assignment/role contract; a parameter does not silently perform a random draw or freeze a roster.

A `group` parameter binds to the caller's permitted producer and owning activation. Once its group exists, retain that actual identity. A declared future group can remain pending only where the receiving capability already supports a pending reference. A required action cannot operate on a not-yet-created group merely because its parameter was valid. A replacement activation never silently receives an earlier reference.

Passing a group does not transfer ownership, expose all of the caller's private state, or authorize another attempt's resources. Instantiations and bound configuration remain on the attempt's captured revision. New publication cannot mutate a current parameter, player-selection definition, or bound group reference. Live state changes continue to use the supported actions rather than overwriting `with` values.

[Q169-Q170](roles-and-player-state.md) accept concrete retained role assignments and explicit player-state fields. A `role` parameter binds the permitted role declaration and activation, while selectors read its current membership. Q168 distinguishes a bound query from a fixed recipient assignment.

[Q201-Q202](pattern-parameters.md) accept registered matcher configuration types and concrete whole-value forwarding and scalar-list-entry rules. They preserve the prohibition on generic untyped maps, action/rule parameters, and deep overrides.

[Q245](ending-scope-presentation.md) accepts a bounded presentation-only exception for a scope's own terminal rules. It permits immediate best-effort finite cues after committed ordinary results, with no gameplay continuations or arbitrary cleanup callbacks.
